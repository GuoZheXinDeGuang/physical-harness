# Round 7：给离线搜索加样本外验证

2026-08-19。

## 先想清楚：shadow 预筛到底加了什么

`search_triggers` 本来就是离线的，不花真实 rollout。所以「用 shadow replay 预筛候选」
如果只是在同一批 trace 上再跑一遍，是零增量。

真正缺的是**样本外估计**：搜索是在它自己搜过的 episode 上打分的，那个排序是样本内的。
贵的是门禁（每个候选 2×N 个真实 episode）。

所以做法是：**把已录的 dev episode 对半切，在一半上搜，在另一半上 shadow 打分**，
按样本外得分排序。零成本，且能在花钱之前把只拟合了搜索半边的候选降下去。

只对**触发器**有效。recovery 候选不能这么筛 —— 换一个修复动作就换一条轨迹，录像不再描述它。

## 实测：预筛确实抓到了过拟合

三组各 60 个种子，样本内 top-1 和样本外 top-1 **每组都不同**。

最有说服力的一例（seeds 2060-2120）：

```
in(r=0.88, fp=0.00)  out(r=0.54, fp=0.12)  shrink=+0.45
observable.finger_gap > 0.079768 for 1 steps, armed from t=41
```

样本内 recall 0.88 且零误报，看起来很值得花门禁；样本外 recall 掉到 0.54、误报涨到 0.12。
**这个候选会白花 240 个真实 episode。**

同时也要说清楚：真正强的信号 shrinkage 基本是 0.00
（`finger_gap < 0.0028` 和 `gripper_effort > 0.0608` 在两半上都是 r=1.00 / fp=0.00）。
预筛不是在推翻搜索，是在**过滤搜索排行榜的尾部噪声**。

## 一个被单元测试抓到的切分缺陷

切分用的是确定性偶/奇交错。写合成测试时，我造的失败模式恰好按 `i % 4 in (1,3)` 排列，
于是偶数索引全是成功 —— 搜索半边单类，`screen` 直接返回空。

这在真实种子上不会发生（种子和成败没有这种对齐），但它暴露了一个真实约束：
**交错切分假设索引顺序与结果无关。** 已在代码里写明，退化切分回落到样本内排序而不是报错。

## 落到代码里

`Preregistration.screen_triggers=True` 时 proposer 用样本外排序。
和 `search_recovery` 一样做成 preregistration 里的显式开关，
这样每次 campaign 用没用它是可审计的，而不是藏在代码版本里。
