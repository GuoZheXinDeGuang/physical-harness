# Round 5：持久事件日志、离线审计、shadow replay —— 并抓到一个真 bug

2026-08-19。

## 日志形状

沿用 dsh 的思路但按具身场景改了比例：一个 chat turn 约 10 个事件，
一个 20Hz / 100 步的 episode 如果逐帧建事件就是 100 行，一次 campaign 上千 episode。
dsh 自己解过同样的压力 —— 把大量 `assistant/chunk` 打包成一行 `text-chunks` 并保留逐块时间差。

Governor 用同样的拆法：
- **行日志**（JSONL，`seq == 行号`）：每 episode 约 3-5 行语义事件
  （`episode/start` / `episode/frames` / `critic/fire`* / `episode/end`）
- **列块**（zlib 压缩、内容寻址）：每 episode 一块，struct-of-arrays 存逐步特征值

40 个 episode = 120 行 + 40 块。

## 重建不变量：链式承诺

要保住 dsh 的「可见 ⟺ 已记录」，但每步存一个 sha256 比数据本身还贵。
改成**链式摘要**：`h_t = sha256(h_{t-1} ‖ digest(view_t))`，整个 episode 只落一个 32 字节值。

关键在于它不循环：链是**在线**从活的 view 算出来的，审计时**从存储的列值重新构造 view 再重算**。
篡改任何一步的值、增删任何一个特征、丢掉任何一步，链都对不上。

两层独立检测：
1. 块自身的内容哈希（存储完整性）
2. 链式承诺（语义：这些值就是当时被拿去决策的值）

实测：40/40 episode 通过审计；改动**一个**存储值（`finger_gap[10] += 0.001`）被抓住。

## Shadow replay 抓到的真 bug

Shadow replay 在不碰仿真器的情况下，用已记录的 episode 评估候选触发器
（Zetta `shadow_replay.py` 的对应物）。它的正确性检验是：
**离线预测的触发步必须和实跑逐步一致。**

第一次跑：**40 个 episode 里 6 个不一致。**

```
seed=3007  shadow=63  live=64  delta=+1
seed=3017  shadow=None  live=60      <- 离线说不触发，实跑触发了
seed=3022  shadow=63  live=60  delta=-3
```

根因：**步索引约定不一致。** `env.rollout()` 产生的 trace 是 0-based，
`governed_rollout` 内部的 `t` 是 1-based，于是每个触发器都**比搜索意图早武装一步**。
`delta=+1` 那几例是纯标号偏移；另两例是早武装让 dwell 窗口提前，
把「本来不触发」变成了「触发」。

修正后：**40/40 完全一致，0 个不一致。**

## 修正对结果的影响（必须重新赚，不能假设沿用）

round 4 的数字是在错误索引下测的。修正后：

| | held-out n=200 提升 | 破坏 |
|---|---|---|
| round 4（早武装一步，有 bug） | +22.0pp | 4 |
| 同一组规则，修正索引 | +17.5pp | 3 |
| **修正后重跑整个 campaign** | **+27.5pp** | **0** |

早武装其实在**帮忙**（+22.0 > +17.5），但它是靠误触发换来的。
在修正后的代码上重新搜索，搜到的规则更好：**+27.5pp，且每一档消融都是 0 破坏**。

## 这一轮说明了什么

日志不是记账，是**可证伪性基础设施**。它抓到的这个 off-by-one，
单元测试抓不到（每个模块自己都自洽），端到端成功率也抓不到（数字反而更好看）。
只有「离线重放必须和在线逐步一致」这个交叉检验能暴露它。
