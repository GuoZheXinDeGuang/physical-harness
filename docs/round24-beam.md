# Round 24：beam 搜索没有解决贪心收敛 —— 因为那不是搜索问题

2026-08-20。三路划分：dev 池 2000-2399 定门禁，**选择区块 2400-2549** 选分支，
held-out 1400-1599 只评一次（1200-1399 在 round 18 用掉了）。

## 为什么 beam 必须有第三个区块

K 条分支需要一个**选择步骤**，而它不能用各分支过门禁的 dev 种子（在门禁用过的数据上选），
也不能用 held-out（只评一次）。所以 preregistration 必须带三路划分。
`run_beam_campaign` 在选择区块与 dev / held-out 有交集时直接报错。

**跳过中间那个区块，正是 beam 搜索最容易做得不诚实的地方。**

## 结果

```
seeding 3 branches from the top-3 candidates:
  b0: running_min(finger_gap) < 0.004473 @58
  b1: finger_gap < 0.016505 @41
  b2: running_range(finger_gap) > 0.063198 @41

gen1  b0 (n=60)  +21.7%  fixed=13 broken= 0  p=2.4e-4  -> 提升
      b1 (n=60)  +13.3%  fixed= 8 broken= 0  p=7.8e-3  -> 提升
      b2 (n=60)   −3.3%  fixed=15 broken=17  p=0.86    -> 分支终止
gen2  b0 (n=131)  +0.8%  fixed= 7 broken= 6  p=1.00    -> 分支终止
      b1 (n=95)   −4.2%  fixed= 3 broken= 7  p=0.34    -> 分支终止

选择区块 (n=150)：b0 +23.3%  b1 +22.7%  b2 +8.7%   -> 选 b0
```

held-out（只评一次，n=200）：**51.0% → 73.0%，+22.0pp，44 修 / 0 破，p<1e-5，零特权**

## 三条负面但有信息量的观察

**1. 三条分支全部止步于深度 1。** beam 探了三个起点，没有一条长出第二条规则。

**2. 选择区块选出的就是贪心 top-1 会选的那条。** 选择区块的排序（b0 > b1 > b2）
与第一代 dev 门禁的排序完全一致。**beam 花了 3 倍成本，得到同一个答案。**

**3. 但这本身验证了搜索的排序是有意义的** —— 排名顺序和真实效果顺序一致，
包括第三名 b2 在门禁上就是负的（−3.3%，修 15 破 17）。

## 为什么 beam 没用：那不是搜索问题

把前面几轮串起来：

- **Round 8** 观察到「每步都通过门禁，终点却更差」，归因为贪心 + 显著性门禁的结构性风险
- **Round 9** 查明那一次的提前收敛是**泄漏的门禁**采纳了不该采纳的 recovery 造成的
- **Round 16** 测出深度受限的真正原因：残余失败里 **42/54 已被检测到、只是修不好**
- **Round 19/21/22** 证实修复原语的天花板是真的，两次手写更强原语都没抬起来

所以：**链止步于深度 1-2，不是因为搜索太贪心，是因为第二条 critic 无事可做。**
再加检测器解决不了「检测到了却修不好」的失败。beam 搜索针对的是一个
(a) 部分是伪影、(b) 现在被别的东西限制住的问题。

## 留下的东西

beam 的机制本身仍然有价值 —— 它把**三路划分**这条纪律固化进了代码
（选择区块与 dev/held-out 有交集直接报错），任何以后要在多个候选之间选择的功能都需要它。
每条分支还会按**自己的**残余率定样本量（round 18 的功效机制），
所以 b0 在第二代拿到 131 个种子而 b1 拿到 95 个 —— 它们残余失败率不同。

**结论：这个方向可以关闭了。** 不是 beam 实现得不好，是它要解决的问题在这个系统里不存在。
