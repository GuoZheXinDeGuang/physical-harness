
### Manipulation-simulation stack feasibility on macOS arm64 (Apple Silicon), headless, CPU-only, 2026 status


**robosuite native MuJoCo bindings (post-1.4 migration)**

As of robosuite 1.4 (Nov 2022) and 1.5 (Oct 2024), robosuite dropped mujoco-py entirely and moved to `import mujoco` (DeepMind's official Python bindings, the same package that gives you 350k steps/sec on your machine). `pip install robosuite` on macOS arm64 pulls a pure-Python wheel plus `mujoco` (which ships native arm64 wheels via PyPI). No compilation, no Rosetta. This is the single biggest reason robosuite is viable on Mac today - it rides on the exact MuJoCo runtime you already validated, not a separate C extension.

*why:* mujoco-py required compiling against GLFW/EGL/GLEW C headers and never had solid osmesa/EGL support on macOS; moving to native mujoco bindings sidesteps that whole legacy toolchain.

*evidence:* https://robosuite.ai/docs/installation.html ; https://github.com/ARISE-Initiative/robosuite (v1.4/1.5 changelog)


**macOS render backend = CGL, and mjpython requirement for on-screen viewer**

robosuite's `robosuite/utils/binding_utils.py` special-cases `_SYSTEM == "Darwin"` and sets `os.environ["MUJOCO_GL"] = "cgl"` (Apple's Core OpenGL / Core Graphics backend), not egl or osmesa - both documented as broken/unsupported on macOS (`MUJOCO_GL=osmesa` rendering tests fail on macOS per mujoco issue #2164; EGL fails to load on Apple Silicon per dm_control issue #207/#365). CGL is what actually works for offscreen framebuffer rendering on Mac. Separately, macOS's window-server threading model means any on-screen GLFW viewer (`mjviewer`) MUST run on the main thread, which is why MuJoCo ships the `mjpython` wrapper and robosuite's docs explicitly say to prefix demos with `mjpython` instead of `python` on Mac. This constraint applies only to the interactive on-screen viewer, not to offscreen/pixel-free rollouts.

*why:* Cocoa/AppKit requires GUI event loops on the main thread; CGL is Apple's native GL context API that MuJoCo's C renderer can target without X11/EGL.

*evidence:* https://github.com/ARISE-Initiative/robosuite/blob/master/docs/installation.md ; https://github.com/google-deepmind/mujoco/issues/2164 ; https://github.com/google-deepmind/dm_control/issues/207


**robosuite's 8 core manipulation tasks and observation-space shape**

robosuite ships Lift, Stack, NutAssembly (Square/Round/RoundHole variants), PickPlace (Can/Bread/Milk/Cereal single or multi-object), Door, Wipe, TwoArmLift, TwoArmPegInHole. Each env exposes `obs_dict` with: robot proprioception (`robotN_proprio-state`: joint pos/vel, eef pose, gripper qpos), and task `object-state` (object pose(s)/relative pose to gripper) as flat low-dim vectors - this is the part that's cheap to obtain, since it comes straight from mjData with zero rendering. If `use_camera_obs=True`, image keys (`agentview_image`, `robot0_eye_in_hand_image`, depth) get added and now cost a render pass per camera per step.

*why:* Designed as a modular RL/imitation-learning benchmark (base for RoboCasa/robomimic); state-only obs is the fast path, camera obs is opt-in.

*evidence:* https://robosuite.ai/docs/source/robosuite.environments.manipulation.html ; https://robosuite.ai/docs/simulation/environment.html


**ManiSkill/SAPIEN experimental macOS support via Vulkan/MoltenVK**

`mani_skill-nightly` (announced March 2025, still nightly-only as of the b21/b22 docs) supports CPU physics simulation on macOS with SAPIEN's renderer running through MoltenVK (Vulkan-to-Metal translation), requiring a manual LunarG Vulkan SDK install with several env vars (VULKAN_SDK, VK_ICD_FILENAMES, DYLD_LIBRARY_PATH). GPU-parallelized simulation (the whole point of ManiSkill's speed advantage) explicitly does NOT work on macOS because it depends on the `physx_cuda` backend, and CUDA does not exist on Apple Silicon. Docs literally say the first run segfaults and a retry is needed, and recommend against using macOS for anything rendering-heavy or for RL training.

*why:* SAPIEN's high-throughput mode is CUDA/PhysX-GPU only; macOS gets the CPU fallback path that was never the intended common case.

*evidence:* https://maniskill.readthedocs.io/en/v3.0.0b21/user_guide/getting_started/macos_install.html ; https://github.com/haosulab/ManiSkill/discussions/1079


**MuJoCo Menagerie arm-model availability (renderer-agnostic, works everywhere native mujoco works)**

Menagerie is just MJCF/XML + meshes, no compiled binary, so every arm loads identically on macOS arm64 as on Linux/CUDA boxes via plain `mujoco.MjModel.from_xml_path()`. Confirmed available: franka_emika_panda (7-DOF + gripper), franka_fr3, universal_robots_ur5e, universal_robots_ur10e, xarm7, kuka_iiwa_14, kinova_gen3, plus several low-cost/bimanual arms (ARX L5, WidowX, ViperX, AgileX PiPER). This is the cheapest path to 'a real arm model' if you bypass robosuite/ManiSkill entirely and just build a bare mujoco harness.

*why:* Menagerie exists precisely to decouple 'good robot models' from any particular simulation framework's packaging.

*evidence:* https://github.com/google-deepmind/mujoco_menagerie


**MuJoCo native threading vs multiprocessing for throughput scaling**

A single `mj_step` is inherently sequential in time (step N+1 depends on step N), so you cannot thread one trajectory to go faster. MuJoCo does support an internal thread pool (`mju_threadpool`, engine-level parallelism for island-based collision/constraint solving within one step), but that only helps on larger/more complex models, not simple ones. Because of Python's GIL, plain Python threads cannot parallelize independent environments. The practical way to use N CPU cores is N independent OS processes (`multiprocessing`/`subprocess`, one MjModel+MjData per process, e.g. gymnasium's `AsyncVectorEnv` / robosuite's own vectorization / EnvPool-style batchers), each running its own single-threaded mj_step loop and getting near-linear scaling up to the physical core count minus a couple for the OS.

*why:* Physics rollout is embarrassingly parallel ACROSS environments/episodes but not WITHIN one trajectory's timestep sequence.

*evidence:* https://github.com/google-deepmind/mujoco/discussions/1522 ; https://mujoco.readthedocs.io/en/stable/programming/simulation.html


**Genesis physics engine's Metal/MPS Apple Silicon path (secondary option, not for manipulation-benchmark tasks)**

Genesis (Genesis-Embodied-AI) advertises native Apple Metal backend support and runs on M-series CPU/GPU. However it is a young, still-unstable project: issue #168 documents a hard crash on Apple Silicon MPS because Genesis's internal solver defaults to float64 and Metal Performance Shaders doesn't support float64 tensors, requiring workaround patches. It also lacks robosuite/ManiSkill's mature library of pre-built manipulation tasks (Lift/Stack/PickPlace/NutAssembly with reward+success functions) - you'd be building the task suite yourself.

*why:* Genesis is built to be GPU-first and cross-backend (CUDA/Metal/CPU) via its own Taichi-like compiler, so exotic backends like Metal get less battle-testing than the CUDA path.

*evidence:* https://github.com/Genesis-Embodied-AI/Genesis/issues/168


**Isaac Sim / Isaac Lab - no macOS path, decisive exclusion**

Isaac Sim/Isaac Lab requires an NVIDIA RTX GPU (Ampere or newer) and CUDA/Omniverse; official docs list only Linux Ubuntu 24.04 and Windows as supported OSes, with GPU as a hard requirement, not an optional accelerator. There is no CPU fallback and no Metal path. The only macOS-touching component is a WebRTC *streaming client* (i.e., you'd need a remote Linux+NVIDIA machine to actually run Isaac and just view/control it from a Mac) - not a local simulation option.

*why:* Isaac Sim is built on NVIDIA Omniverse/PhysX which is CUDA-native end to end.

*evidence:* https://isaac-sim.github.io/IsaacLab/main/source/setup/installation/index.html ; https://github.com/isaac-sim/IsaacSim


**REUSABLE**
- Adopt robosuite (pip install robosuite; requires mujoco which auto-installs as an arm64 wheel) as the primary manipulation stack: it rides directly on the same native mujoco Python bindings already benchmarked at 350k steps/sec, needs zero macOS-specific patching for state-only rollouts, and ships a mature 8-task suite (Lift, Stack, NutAssembly, PickPlace, Door, Wipe, TwoArm*) with both low-dim proprio/object observations and optional camera observations.
- Default to state-only observations (use_camera_obs=False) for the harness's hot loop - this is the biggest lever for both correctness and throughput on Mac: it avoids CGL/offscreen-rendering entirely (the one genuinely fragile part of the stack), and MuJoCo's own contact/joint state already contains everything a manipulation policy needs for grasp detection, success checking, and reward shaping.
- If pixels are truly required for a subset of episodes (e.g. periodic visual logging/eval), explicitly set MUJOCO_GL=cgl before importing mujoco/robosuite, run any code path that opens a GLFW/mjviewer window via `mjpython` instead of `python`, and treat the first offscreen render call in a fresh process as a possible segfault-and-retry (matches the ManiSkill mac install doc's documented behavior) - do not assume egl or osmesa will work, both are documented broken on macOS.
- For throughput, parallelize across CPU cores with independent OS processes (multiprocessing/AsyncVectorEnv-style), one MjModel/MjData/robosuite env instance per process; do not attempt to thread multiple environments in Python (GIL) or expect within-model MuJoCo threading (mju_threadpool) to substitute for cross-environment parallelism - that only helps within one step of one model, not across an environment batch.
- Keep MuJoCo Menagerie (google-deepmind/mujoco_menagerie) as the source of truth for arm MJCF assets (Franka Panda, UR5e, xArm7, etc.) if the harness ever needs to go outside robosuite's bundled models - these load identically on macOS since they're plain XML/mesh assets with no compiled backend dependency.
- Recommend ManiSkill (mani_skill-nightly + SAPIEN/MoltenVK) only as the fallback, and only for CPU-simulation + basic-rendering smoke tests or task authoring/debugging - explicitly do not use it for the harness's real training/eval throughput path on Mac, since GPU parallel simulation (its core value proposition) is unavailable there and the install itself is nightly/experimental with a known first-run segfault.

**ANTIPATTERNS**
- Do not use mujoco-py (the old OpenAI fork) or any tutorial that references it - it's deprecated, requires manual GLEW/GLFW compilation, and never had reliable macOS support; robosuite itself abandoned it in v1.4 for exactly this reason.
- Do not set or rely on MUJOCO_GL=egl or MUJOCO_GL=osmesa on macOS - both are documented as non-functional (EGL fails to load on Apple Silicon per dm_control #207; osmesa rendering tests fail on macOS per mujoco #2164). Only cgl works for offscreen, and glfw only works with mjpython for on-screen.
- Do not pick Isaac Sim/Isaac Lab or plan around eventual CUDA support on Mac - there is no CPU or Metal fallback in the product at all, it is a hard NVIDIA-GPU dependency end to end; this is a dead end worth ruling out immediately rather than revisiting.
- Do not expect ManiSkill's advertised massive-parallel GPU throughput numbers to apply on Mac - those figures come from the physx_cuda backend, which is categorically absent on Apple Silicon; only CPU-single-env numbers are realistic there.
- Do not try to parallelize a single environment's rollout across Python threads to use multiple cores - the GIL blocks it and mj_step is sequential in time anyway; use multiprocessing/independent processes instead.
- Do not adopt Genesis for a manipulation-task benchmark harness today - its Apple Silicon/Metal path has open, unresolved crash bugs (float64/MPS incompatibility) and it lacks a mature built-in manipulation task suite comparable to robosuite's, so you'd be debugging the engine and building the tasks simultaneously.

### Capability Seam pattern (DeepSeek Harness on Cordis): how Service Definition / Provider / Consumer roles are declared an


**Service Definition = abstract Service subclass + declared ctx key**

Each seam package (e.g. dsh-shell, dsh-fs, dsh-code-runtime) exports an `abstract class X extends Service` whose constructor calls `super(ctx, '<name>')`, plus a TypeScript `declare module '@deepseek-ai/cordis' { interface Context { shell: ShellExecutor } }` augmentation that gives every consumer a typed `ctx.shell`. The class declares abstract methods (`resolve`, `run`, `start` for shell; `readText`/`writeText`/`editText` for fs) that every Provider must implement, plus optional overridable getters (e.g. `sandboxMode`) with a safe default. The Service base class's constructor calls `ctx.reflect.provide(name, this, check)`, which both registers the instance under that name AND ties its lifetime to the owning plugin's fiber — the service vanishes automatically when the fiber unloads. Only one instance may be registered per name at a time; mounting a second Provider throws.

*why:* Splits the interface (what every future backend must honor, including non-obvious semantics like 'run() never rejects on nonzero exit, only on infra failure') from any one implementation, so a consumer can be written once against the abstract class and any Provider can be swapped in later purely through config.

*evidence:* packages/shell/shell/src/index.ts:39-104 (ShellExecutor); packages/fs/fs/src/index.ts:42-90 (FileSystem); vendor/cordis/src/service.ts:29-58 (Service constructor calling ctx.reflect.provide)


**Service Provider = concrete subclass mounted as a Cordis plugin**

A provider package (dsh-bash-local) exports a class extending the abstract Service Definition class, declares `static inject = ['subprocess']` (its own hard dependencies), a `static Config` schemastery schema for its plugin-config row, and implements the abstract methods by delegating to lower seams it injects (bash-local's `run`/`start` spawn through `ctx.subprocess`). Constructors read schema-defaulted config, validate cross-field constraints eagerly (`assertServiceableBashConfig`), and — critically — DON'T close over the resolved value; they store a `source: () => ResolvedConfig` thunk and read `this.config` through a getter, so a later settings write can repoint the thunk without recreating the service.

*why:* Providers own execution mechanics and defaulting; the seam's abstract contract stays free of platform detail so an alternate provider (fs-sandbox, fs-e2b) can honor the exact same consumer-facing contract while confining or remoting execution.

*evidence:* packages/shell/bash-local/src/index.ts:105-163 (class LocalBashExecutor, config source thunk)


**Consumer = plugin function that injects the seam and registers a model-facing tool**

A consumer package (dsh-tool-bash) is a plain `apply(ctx, config)` function, `export const inject = ['tools', 'shell', 'systemPrompt', 'shellEnv']`. At apply time it calls `ctx.shell.resolve(request)` then `ctx.shell.run(spec)`/`ctx.shell.start(spec)` — it never imports a concrete provider class, only the seam's exported types. It registers itself onto the NEXT seam down the chain (`ctx.tools.register(defineTool({...}))`) and a prompt section (`ctx.systemPrompt.section({...})`), so a tool Consumer is simultaneously a Provider into the tools seam.

*why:* Keeps model-facing surface (schema, description, presentation) decoupled from execution backend; swapping bash-local for bash-sandbox changes nothing in tool-bash.

*evidence:* packages/shell/tool-bash/src/index.ts:30-31,190-243,340-345 (inject list, ctx.tools.register / ctx.systemPrompt.section, ctx.shell.resolve calls)


**"Registrations are effects": ctx.effect() + returned disposer**

Any contribution a plugin makes to a shared registry — a settings namespace, a tool, a prompt section — runs inside `ctx.effect(() => { register(); return () => unregister() }, label)`. `Fiber.effect()` (vendor/cordis/src/fiber.ts) accepts a sync/async function, a generator yielding several disposers, or a promise, and always normalizes to a disposer chain owned by the calling fiber. When that fiber's plugin unloads (config change, HMR reload, teardown), Cordis runs every collected disposer in reverse, so the registry entry disappears cleanly with no manual bookkeeping at the call site. `SettingsProvider.register()` is the canonical example: `this.ctx.effect(() => { this.registrations.set(ns, registration); return () => this.registrations.delete(ns) }, ...)`.

*why:* Buys reload-safety and hot-swap: any plugin (a Provider, a tool, a settings section) can be unmounted and remounted at runtime (dev HMR, a live provider swap) without leaking stale registry entries or requiring every consumer to hand-write teardown logic.

*evidence:* vendor/cordis/src/fiber.ts:403-418 (effect() overloads and disposer normalization); vendor/cordis/src/service.ts:36-58 (constructor ties registration to fiber via ctx.reflect.provide); packages/settings/settings/src/index.ts:432-445 (register() wrapping ctx.effect)


**Profile → bundle → patch layered config-row composition**

A profile is a directory (`$DSH_HOME/profiles/<name>`) with a `package.json` naming an ordered `dsh.profile.bundles` list and its own `cordis.patch.yml`. A bundle is an npm package whose manifest points at a `cordis.patch.yml` containing a top-level YAML array of `{id, name, config, disabled, insert}` rows (dsh-base's is ~350 lines, one row per plugin: llm, session, tool-bash, fs-sandbox, etc.). Composition is one fold, `applyEntryPatches([], allLayersFlattened, warn)`, over an INITIALLY EMPTY entry list: each bundle layer in listed order, then the profile's own patch file, then the home-level patch file, then any `--patch` CLI overlay. Within `applyEntryPatches`: an `insert` entry with no `id` appends new top-level rows (or, with an `id`, appends into a named group's children); a non-insert patch entry requires an `id`, looks the row up in a map built by walking the tree so far, and does `target[key] = value` for every other field in the patch object — this REPLACES that field wholesale (typically the whole `config` object), never deep-merges, so a later layer's patch must restate every field of `config` it wants to keep. The exact same call (`renderConfigDump`, `dsh --dump-config`) is used both to actually boot and to preview the composed tree offline, so there is no drift between what a config-dump shows and what mounts.

*why:* Gives every part of the harness one mutable, inspectable, diffable config surface with deterministic last-write-wins semantics per row id, letting a deployment (web vs headless), a user profile, and a one-off `--patch` overlay each override exactly the rows they care about without forking the base bundle or fighting a deep-merge ambiguity.

*evidence:* docs/architecture.md:15-37 (profiles/bundles/layering description); packages/bundle/base/cordis.patch.yml:1-15,347-360 (patch header + example rows); packages/boot/app-boot/src/profile.ts:227-283 (loadProfile resolving bundle layers + user patch layer), 285-300 (composeEntries calling applyEntryPatches); vendor/include/src/index.ts:58-124 (applyEntryPatches: insert vs id-targeted whole-field-replace)


**Settings seam: hot re-read on the hot path via a getter, not a snapshot**

`ctx.settings` (dsh-settings) exposes `register(ns, schema, {base, validate}) -> SettingsScope<T>` where `SettingsScope.get()` returns the CURRENT resolved value (schema defaults < composition `base` < user document layer) and `.watch(cb)` fires on committed changes. The shared helper `installSettingsSection(ctx, ns, schema, entry, hooks)` does the wiring generically: it injects `settings` optionally (`ctx.inject(['settings'], ...)`), registers the namespace with the plugin's own composition config as `base`, calls `hooks.setSource(() => scope.get())` to hand the consumer a THUNK (not a value), and re-calls `setSource`/`onChange` on every watched change and on settings-provider teardown (falling back to the static `entry`). Concretely for `agent-loop`'s `maxParallelToolCalls`: the constructor does `let source = () => entry; this.config = { ..., get maxParallelToolCalls() { return source().maxParallelToolCalls } }`, then `installSettingsSection(..., { setSource: (current) => { source = current }, onChange: () => {} })`. The tool-call scheduler (`tool-calls.ts:131`) reads `const { maxParallelToolCalls } = ctx.agentLoop.config` FRESH at the start of each new parallel-dispatch group (`tool-calls.ts:199`, `while (... inFlight.size < maxParallelToolCalls)`), so a settings write mid-turn changes the cap for the NEXT group without touching calls already dispatched in the current group.

*why:* Lets a user-editable, hot-reloaded config value (edited live in a settings UI or file) reach a scheduler making per-group decisions on a hot path, without ever tearing down or racing the in-flight work that decision already committed to — the getter/thunk indirection is what makes 'live' config compatible with in-progress async work.

*evidence:* packages/settings/settings/src/index.ts:863-897 (installSettingsSection); packages/core/agent-loop/src/index.ts:246-251,317-345 (AGENT_LOOP_SETTINGS_SCHEMA, config getter + installSettingsSection call); packages/core/agent-loop/src/tool-calls.ts:131,199 (fresh read per dispatch group)


**Capability-seam completeness rule enforced by the capability graph doc**

docs/capability-seams.md is machine-generated (`scripts/gen-doc-graphs.ts`) from the actual Cordis declarations in the repo: it walks every package for `ctx.<key>` declarations, classifies each as owner/implementation/consumer, and asserts completeness — a package that only implements or only consumes without an owning Service Definition would fail the generator's guard. CLAUDE.md states the rule explicitly: 'A capability seam comprises Service Definition / Service Provider / Consumer roles. It is complete, never one role; split only when roles evolve independently.'

*why:* Prevents architecture drift where someone adds a capability by bolting an implementation directly onto a consumer (skipping the abstract seam), which would make future backend swaps require touching the consumer again.

*evidence:* docs/capability-seams.md:1-6,483 (generation banner + maintenance-mode note); CLAUDE.md 'A capability seam comprises Service Definition / Service Provider / Consumer roles...' rule


**REUSABLE**
- Keep the three-role discipline (Definition/Provider/Consumer) as PLAIN Python: an abc.ABC or typing.Protocol per seam declaring the methods every backend must implement (mirrors ShellExecutor/FileSystem) with docstrings pinning non-obvious semantics (e.g. 'run() never raises on nonzero exit'); a Provider is a subclass instantiated during boot; a Consumer only imports the ABC/Protocol types, never a concrete Provider class. This is pure architecture, costs nothing to port, and is the actual value of the pattern.
- Keep 'registrations are effects': every registry mutation a Provider/Consumer makes (a tool, a settings section, a hook) returns a disposer (a zero-arg callable), collected on a contextlib.ExitStack owned by that plugin's setup call; teardown/hot-swap runs the stack in reverse. No fiber tree or reflection needed for ~8 seams — one ExitStack per mounted component is enough to get clean unmount/remount.
- Keep id-addressed, ordered config-row layering with whole-field-replace patch semantics: represent the composed tree as a flat list of {id, module, config, disabled} dict rows; compose by folding layers (base bundle -> profile patch -> user patch -> CLI overlay) where an insert entry appends rows and an id-targeted patch does target.update(overrides) (dict.update, i.e. field-level replace, never deep-merge) exactly like vendor/include's applyEntryPatches. This is ~40-60 lines of Python and gives deterministic last-write-wins overrides per row without a plugin loader.
- Keep the settings hot-read discipline: any service exposing a config value read on a hot path stores a Callable[[], T] (or watches an update event that repoints one), and any decision loop reads the getter fresh at each new unit of work (each dispatch batch, each request) rather than snapshotting into a local at loop entry. In Python this needs no framework -- just the getter-not-value convention plus a small Settings object with register(ns, default) -> (get, watch).
- Keep a minimal typed Context: a dataclass or SimpleNamespace with one attribute per known seam (ctx.shell, ctx.fs, ctx.llm, ...), populated in composition order during boot; a Provider's setup(ctx, config) function asserts its own hard dependencies are already set (mirrors static inject but as a plain assert/None-check) instead of Cordis's dependency-graph solver -- fine at ~8 seams where boot order is just the config-row order.
- Keep the generated-graph completeness check as a lightweight lint, not runtime machinery: a short script that scans provider/consumer modules for which ABC each implements/imports and fails CI if a capability has an implementation but no owning Definition module, mirroring docs/capability-seams.md's generator without needing Cordis's runtime reflection to produce it.

**ANTIPATTERNS**
- Do not port Cordis's full fiber tree with runtime dependency-graph solving, hot module reload of the plugin graph, and `ctx.inject([...], callback)` reactive service-appearance waiting -- for ~8 statically known seams this is enormous machinery (vendor/cordis/src/fiber.ts is thousands of lines) to buy dynamic remounting you don't need; a linear list of setup(ctx, config) calls executed once at boot is sufficient.
- Do not port the generic typed event bus (waterfall/serial/emit event maps with TypeScript declaration-merging `interface Events {...}` augmentation, e.g. fs/write-intent, agent/pre-step). This exists to let an open ecosystem of third-party plugins intercept/veto product-owned lifecycle points; for 8 first-party seams you fully control, direct method calls between explicitly injected services are simpler and just as correct -- add a specific hook point (a plain list of callables) only where you actually need interception, not a generic bus up front.
- Do not port Schemastery (a full runtime schema/validation/defaulting/UI-metadata DSL used to also drive a web settings page with redaction and revision-based optimistic concurrency). If there's no live web settings UI, use dataclasses + manual validation (or pydantic if already a dependency); building a bespoke schema system to describe 8 seams' config is pure overhead.
- Do not port the settings seam's full base/user-layer/revision/SettingsConflictError optimistic-concurrency plus redact-for-wire descriptor machinery -- that complexity is justified by a multi-surface product (web UI editing settings live while a CLI/agent also reads them). A single in-process config object with an explicit reload() and the getter-indirection discipline (see mechanisms above) gets the load-bearing property (hot value, safe mid-flight) without the conflict-detection/redaction layers.
- Do not port the two-anchor npm bundle-resolution and profiles/node_modules symlink-healing machinery (packages/boot/app-boot/src/profile.ts:healProfilesModuleFallback) -- this solves an npm/pnpm-specific packaging problem (out-of-tree plugins needing the host's hoisted dependency versions). Python providers loaded via ordinary imports (installed packages or files already on sys.path) don't have this problem; skip it entirely.
- Do not port the Service class's callable-service machinery (`[Service.invoke]`, `createCallable`, proxy-wrapping so a service instance is itself invocable) -- it's a TypeScript ergonomics trick (e.g. `ctx.logger('label')`) with no material benefit in Python where a plain method call (`ctx.logger.log(...)`) is equally ergonomic.
- Do not port YAML `!!js` inline-JavaScript config expressions (arbitrary code execution inside config files, e.g. `mode: !!js process.env.DSH_PERMISSION_MODE ?? 'workspace-write'`) -- convenient in a TS-native loader but a real security/complexity liability to replicate in Python; use plain env-var interpolation syntax (e.g. `${VAR:-default}`) resolved by the loader instead of embedding a code-eval escape hatch in config.
- Do not port Typert (the runtime type-registry auto-generating RPC descriptors for a browser API from Zod schemas) or the full agent-team/workflow/goal orchestration subsystems -- these are product surfaces (web app, multi-agent teams) layered ON TOP of the seam pattern, not part of the pattern itself; a harness with 8 seams and no browser client needs none of it.

### Rollout Infrastructure Architecture (rollout_runtime/) behind the claimed 20.6x throughput / 11.1x inference speedup


**Three-layer split: Gateway (control plane) / EnvWorker (data plane) / RolloutWorker (inference-serving plane)**

RuntimeGateway (gateway/gateway.py) is a single-writer asyncio object that owns session lifecycle, admission, idempotency, and routing; it never touches env state or model weights. RuntimeEnvWorker (workers/env_worker.py) owns all environment execution state (SessionSlot, EnvPool) and expands the atomic 'policy_step' command into observe -> request_inference -> chunk_step itself -- the Gateway only ever sends one opaque command and gets one result back. RuntimeRolloutWorker (workers/rollout_worker.py) is a persistent serving loop that keeps the policy loaded and never sees a whole episode, only a continuous stream of InferenceRequest objects pulled competitively (work-stealing) from a shared request channel.

*why:* Lets each plane scale/fail independently: many EnvWorker ranks (CPU-bound env stepping) can share a small number of RolloutWorker ranks (GPU-bound, persistent-weights inference), and the Gateway can run on a CPU-only driver process with zero GPU footprint. It also enforces a hard invariant ('Gateway and EnvWorker never co-mutate the same session state') that makes concurrent dispatch safe without a global lock.

*evidence:* rollout_runtime/gateway/gateway.py:1-18 (class docstring 'D2'), rollout_runtime/workers/env_worker.py:1-25, rollout_runtime/workers/rollout_worker.py:1-25


**Session lifecycle state machine + sticky worker binding**

SessionManager (gateway/session_manager.py) is the sole writer of a strict state graph: CREATING -> READY -> CLOSING -> CLOSED, with READY -> LOST on heartbeat loss and CREATING -> FAILED on bind failure. Every transition is validated against ALLOWED_SESSION_TRANSITIONS; illegal edges raise InvalidTransition. A session is bound once to one EnvWorker rank + binding_token (an opaque uuid) at create_sessions time; all subsequent commands for that session must carry a matching token or get STALE_BINDING.

*why:* A physical/simulated environment carries state that cannot migrate mid-episode, so sessions must be sticky to one worker. The explicit state machine (rather than ad hoc flags) makes 'is this session usable right now' a single lookup and prevents races between concurrent create/close/lease-expiry paths.

*evidence:* rollout_runtime/gateway/session_manager.py:23-79 (state table + docstring), rollout_runtime/gateway/gateway.py:698-756 (_create_session)


**Dynamic slot placement + warm/cold slot reuse (EnvPool)**

EnvPoolManager keys pools by env_spec.digest() so any two sessions with an identical env config share one pool/one built simulator process. EnvPool.acquire_or_grow() first tries a synchronous pop from warm_free_slots (already-built, idle simulator lanes); only when none are free does it reserve capacity under a state lock and cold-create a new slot via asyncio.to_thread (blocking simulator construction), bounded by a semaphore(8) and env_spec.effective_max_pool_size(). Idle slots can later be shrunk from the tail by a maintenance loop (shrink_idle).

*why:* Building a real simulator (subprocess or GPU-batched) can take seconds; reusing warm slots turns repeated reset/close cycles (as happens constantly in RL rollout) from 'seconds of cold-start' into 'a list.pop()'. The reserve-then-build pattern with a state lock specifically fixes a measured race where N concurrent create_session calls would each see 'pool does not exist' and build N orphaned pools, corrupting slot->lane mapping.

*evidence:* rollout_runtime/workers/env_worker.py:360-420 (acquire_or_grow, _reserve_cold_create_locked), rollout_runtime/workers/env_worker.py:2074-2124 (_ensure_pool docstring describing the found/fixed race)


**SlotGroupCoalescer: lockstep rendezvous batching for GPU-vectorized envs**

For pools declared 'lockstep_vector' (one shared GPU-batched simulator instance backing many logical env lanes, e.g. ManiSkill), each session's chunk_step call spawns its own task; SlotGroupCoalescer makes the first arrival the 'leader', which waits until every currently-running lane in that pool has registered (or a window_seconds timeout) and then issues exactly one core.chunk_step(slots, blocks) call, distributing results back per lane. Absent lanes are carried forward via a hold action rather than blocking the whole group.

*why:* A GPU-batched vector env is a single state machine (ManiSkill enforces 'must call _gpu_fetch_all before _gpu_apply_all again'), so concurrent per-session calls into it would corrupt state; naive serialization would also destroy the whole point of GPU batching (one big matmul vs many tiny ones).

*evidence:* rollout_runtime/workers/env_worker.py:875-905 (class docstring), rollout_runtime/workers/env_worker.py:2694-2745 (_step_slot dispatch to coalescer only when pool.lockstep)


**Transport: bounded Channel command/control/result planes, InProc vs Ray, msgpack framing**

CommandTransport is a Protocol with two implementations: InProcTransport (same event loop, directly awaits the worker handler -- zero serialization) and RayChannelTransport (three independent rlinf Channel actors: rr-cmd bounded per-rank command queue, rr-ctl independent control queue so cancel/heartbeat never queue behind a running env step, rr-res result flow-back keyed by request_id). Every channel is created with an explicit maxsize (rlinf's default of 0 is unbounded and would defeat backpressure); put_nowait raising QueueFull is the backpressure signal, translated into ErrorCode.QUEUE_FULL. Frames are packed via msgpack (api/wire.py), not Ray's pickle, to keep serialization to one well-defined, byte-countable format.

*why:* Separating control from data traffic means a hung/slow env step can never delay a cancel or heartbeat probe for the same or other ranks. Bounded queues turn 'system is overloaded' into an immediate, explicit rejection instead of unbounded memory growth and unpredictable latency.

*evidence:* rollout_runtime/transport/base.py:1-20, rollout_runtime/transport/ray_channel.py:1-43 (module docstring re: unbounded maxsize=0 pitfall), rollout_runtime/api/wire.py:1-20


**Idempotency, late-result handling, and RPC-timeout-is-not-cancellation**

OperationRegistry.begin() computes a fingerprint from (operation, session_id, payload); a repeated request_id with a matching fingerprint returns the cached terminal result (or current in-flight status) without touching the env again; a mismatched fingerprint raises IDEMPOTENCY_CONFLICT. Separately, once transport.command_timeout_seconds elapses the caller gets DEADLINE_EXCEEDED but the operation record stays RUNNING (not failed); the real result, when it eventually arrives on the result channel, is absorbed by Gateway._absorb_late_result and finalizes the operation -- so a slow response is never misclassified as a failure and never silently retried.

*why:* RL rollout clients retry on timeout; without request-level idempotency a retried policy_step could double-step the environment and corrupt the trajectory. Separating 'RPC timeout' from 'operation failed/cancelled' avoids the classic distributed-systems bug of treating a slow-but-alive worker as dead.

*evidence:* rollout_runtime/gateway/operation_registry.py:231-280 (begin), rollout_runtime/gateway/gateway.py:266-318 (_absorb_late_result), tests/runtime/test_e2e_fake.py:486-524 (assertion 5)


**Staged cancellation (queued / inference / env_step / done) with 3 substantive outcomes plus a 4th 'outcome unknown' state**

ActiveRequest.stage tracks where a command currently is. cancellable is true only in queued/inference (no side effect yet). (1) Cancelled before dispatch: Gateway sees the operation already terminal in OperationRegistry and never touches the worker -- side_effect_applied=False. (2) Cancelled while waiting on inference: the worker cancels the pending asyncio.Future in InferenceClient; a subsequently-arriving action is judged 'late' via a (binding_token, episode_id) match check in InferenceClient.deliver and discarded/counted -- side_effect_applied=False. (3) Cancelled after the env step has started: cancellation is a no-op for the step itself (asyncio.to_thread cannot be interrupted mid-call); the operation is left RUNNING, side_effect_applied is honestly reported True, and the caller is told to wait for the real result. A logically separate 4th state, OUTCOME_UNKNOWN, covers a worker becoming completely unreachable mid-operation -- the result is WORKER_LOST and is never auto-replayed.

*why:* An environment step, once started, is a physical/simulated side effect that cannot be undone; pretending to cancel it would silently corrupt trajectory data. Making all three (four) outcomes explicit and separately tested prevents 'cancel' from ever being conflated with 'rolled back' or with 'timed out'.

*evidence:* rollout_runtime/workers/env_worker.py:191-227 (ActiveRequest/STAGE_* + cancellable), rollout_runtime/gateway/gateway.py:1154-1213 (cancel_request message construction), tests/runtime/test_e2e_fake.py:574-780 (assertions 6a/6b/6c + fourth-state test)


**Dynamic batching on the policy side: compat_key bucketing + max_batch_size/max_wait_ms trigger + fairness quotas + version fence**

InferenceBatchScheduler (workers/batch_scheduler.py) buckets pending requests by compat_key (a sha256 of policy_id, model_version, obs schema digest, canonicalized inference params, device, dtype, and hard constraints -- core/policy_inference.py). A batch fires when a bucket's selectable count hits max_batch_size or the oldest selectable request has waited max_wait_ms, whichever first; RolloutWorker.execute_batches waits exactly the computed time_until_ready rather than polling. Fairness is enforced via per-application/per-session in-flight quotas checked incrementally while selecting a batch, so one tenant cannot monopolize a batch slot. update_weights raises a 'version fence' that blocks new batches (next_batch returns []) until in-flight batches drain, swaps weights, then lowers the fence -- guaranteeing no batch ever mixes two model versions.

*why:* This is the mechanism that produces the '11.1x inference speedup': batching many envs' observations into one forward pass amortizes fixed model overhead. compat_key prevents batching requests that would silently produce wrong results (different obs schema, dtype, or a cuda_graph-fixed batch shape). The version fence makes online weight updates (needed for the self-evolving-policy training loop) safe without stopping the whole serving loop.

*evidence:* rollout_runtime/workers/batch_scheduler.py:1-30 (module docstring, full requirements list), rollout_runtime/core/policy_inference.py:110-155 (compute_compat_key), rollout_runtime/workers/rollout_worker.py (update_weights, ~line 300-340)


**Fake backend: deterministic env + deterministic policy, both with fault-injection hooks, making the whole control plane CPU-testable with no simulator and no model**

FakeEnvCore (backends/fake/env.py) is a pure-numpy state machine: observation = f(seed, step), action-checksum tracked per slot, and four injectable fault modes (fail_on_step/fail_on_reset for error-isolation tests, step_delay_seconds to simulate a slow env step so cancellation-state-3 tests are reachable, hang_on_step+hang_timeout_seconds for isolating a truly stuck worker). FakePolicyCore (backends/fake/policy.py) similarly derives its action chunk deterministically from (session_id, episode_id, step_index) so idempotency/out-of-order assertions can do exact byte comparison, and exposes hold()/release() (an asyncio.Event gate) plus delay_seconds/jitter_seconds to make inference hang or arrive out-of-order on demand, plus fail_sessions/fail_policy_ids for per-request POLICY_FAILURE injection. Because injection is keyed at the env-spec/config level, a different env_config produces a different pool digest, so 'only this one session explodes' needs no special test hook.

*why:* This lets all 8 e2e control-plane assertions (ordering under concurrency, out-of-order correlation, late-result rejection, idempotent replay, all cancellation states, backpressure QUEUE_FULL, error isolation) be exercised deterministically on a laptop CPU in milliseconds, with no MuJoCo/robot simulator and no real 7B-parameter VLA model in the loop -- letting the control-plane logic (which is where most distributed-systems bugs actually live) be validated independent of, and far faster than, the real workload.

*evidence:* rollout_runtime/backends/fake/env.py:1-33 (module docstring, fault-injection table), rollout_runtime/backends/fake/policy.py:1-25, tests/runtime/test_e2e_fake.py:1-19 (module docstring listing the 8 assertions)


**REUSABLE**
- Bounded queues with explicit reject-when-full (QueueFull -> immediate error) instead of unbounded buffering: cheap to add even in a single process (e.g. a maxsize'd multiprocessing.Queue) and prevents a slow policy step from silently blowing up memory or destroying step-time determinism.
- Total-function worker calls: wrap each env-worker-process's step/reset in try/except and return a typed error/result object rather than letting an exception kill that worker; keeps one bad reset (a MuJoCo XML edge case, a NaN state) from taking down the whole N-env pool.
- A fake/deterministic env + fake/deterministic policy pair for driver-loop testing: even for a single-machine harness, build a trivial numpy-only env and policy so the orchestration logic (batching, error handling, episode bookkeeping) can be unit-tested in milliseconds without paying MuJoCo startup cost on every CI run.
- Pool-by-config-digest sharing: if you ever run multiple env variants (different XML/task configs) in one process pool, key your worker pool by a hash of the config so identical configs reuse the same warm worker set instead of re-spawning.
- Synchronous batched policy inference across all N envs each control step: collect all N observations, run one batched forward pass (numpy/torch on CPU or MPS), scatter actions back -- this alone captures most of the 'dynamic batching' throughput win without needing compat_key bucketing, a scheduler, or async request/response plumbing, because on one machine every env shares the same policy/dtype/device by construction.
- A three-stage cancellation/interrupt model (not-yet-started / waiting-on-policy / mid-step) is cheap to implement (one enum field per in-flight request) and gives you a correct, testable answer to 'what does stopping a rollout early actually do to trajectory data' -- worth keeping even at small scale.
- Concrete single-machine architecture: one process (or a small ProcessPoolExecutor with N workers, since MuJoCo stepping is CPU-bound and Python threads won't parallelize it past the GIL) holding N MuJoCo env instances; N sized to (physical performance cores - 1 to 2, reserved for the main/policy-inference thread) -- e.g. on an Apple Silicon M-series laptop with 8-12 performance cores, N in the 8-16 range gives close to linear scaling before efficiency-core/thermal contention flattens the curve; verify empirically with a step-throughput microbenchmark rather than assuming linearity past ~2x core count. Use one bounded result queue (maxsize ~2N) from workers back to the driver for backpressure, and do policy inference as one synchronous batched call per control step in the driver rather than a separate serving process.

**ANTIPATTERNS**
- Ray Channel actors / multi-process command-control-result transport with heartbeat probing and per-rank health tracking: this solves 'a worker rank can independently die on a different machine/GPU node,' which does not apply when everything is one process on one laptop -- a crash there takes down the whole run anyway, so there is nothing partial to detect or reap.
- Three network-addressable planes (Gateway / EnvWorker / RolloutWorker) with msgpack-framed RPC between them: for a single machine this is pure overhead -- direct in-process function calls (or at most in-process asyncio tasks, as InProcTransport already demonstrates) get you the same logical separation without serialization cost or an operation registry to track RPC state.
- SlotGroupCoalescer's leader/rendezvous batching for a single shared GPU-vectorized simulator state machine: this exists because ManiSkill's single GPU-batched env instance corrupts if two lanes call reset/step concurrently. Per-process MuJoCo (CPU, PER_SLOT_FORM equivalent) has fully independent env instances with no shared state machine to protect, so there is nothing to coalesce or rendezvous on.
- Admission control with per-application/per-tenant session and in-flight quotas: this is multi-tenant fairness infrastructure for a shared cluster serving multiple research teams/jobs; a single researcher's local training loop has exactly one tenant and gains nothing from it.
- Dynamic pool growth/shrink with cold-create semaphores and a min/max pool-size floor: solves 'many different env-spec digests show up unpredictably at runtime on a shared cluster.' A local harness normally knows N up front for the whole run, so just spawn N workers once and skip the grow/shrink machinery entirely.
- Weight-update version fencing across concurrently in-flight inference batches: needed when a serving system is fielding requests from many remote EnvWorkers while training updates weights mid-flight. On one machine, if you update policy weights between rollout batches you can just... not fire new batches during the update (a simple flag check in your driver loop), no fence/drain protocol required.
- The full RuntimeErrorInfo/ErrorCode taxonomy (WORKER_LOST, STALE_BINDING, OUTCOME_UNKNOWN, IDEMPOTENCY_CONFLICT, etc.): most of these encode distributed partial-failure ambiguity (worker unreachable vs. worker slow vs. worker dead) that simply does not exist in a single process -- an exception there is unambiguous. Keep a small local error enum (env crashed / policy failed / timeout) instead of importing this whole vocabulary.

### DRIVER + DURABLE LOG: how dsh-agent-loop drives a session through turn/step boundaries while dsh-session keeps an append


**Phase state machine (idle | maintenance | running) with the AbortController owned BY the phase**

`type Phase = {kind:'idle'; lastTurn} | {kind:'maintenance'; abort; lastTurn; wakeRequested} | {kind:'running'; abort; turn; step; wakeRequested}` (agent.ts:38-46). The AbortController is a FIELD OF THE PHASE OBJECT, not of the agent. Consequences: (a) `cancel(cause)` is just `this.phase.abort.abort(cause)` and is a no-op when idle — there is no active work to cancel and cancellation never 'arms' future work (agent.ts:134-140); (b) the abort reason IS the structured cause (`{kind:'user'|'parent'|'hook'|'disposed'}`), read back at the turn boundary to write `turn/end {reason:{kind:'aborted', reason}}` (agent.ts:303-305); (c) a signal is never reused across turns — at the end of a turn that still has queued work, `phase.abort = new AbortController(); phase.wakeRequested = false; phase.step = 0` (agent.ts:325-328), so a stale abort cannot poison the next turn and a latch set on the old controller is deliberately made stale; (d) public status is a projection of the phase, `idle|maintenance -> 'idle'`, `running -> 'running'`, published only on transitions via `setPhase` (agent.ts:99-111), and a companion invariant fails on a repeated no-op status transition (agent/invariant.ts:15-24). `runMaintenance(job)` claims the idle phase with its OWN controller so off-turn work (compaction, title generation) is cancellable by exactly the same `cancel()` call while public status stays `idle` (agent.ts:142-162). The driver body is `kick(): while (await this.turn()) {}` wrapped in try/catch/finally — every reported failure and cancellation is CONTAINED at the driver boundary, and the finally clause is the only place that returns the phase to idle (agent.ts:210-223).

*why:* Cancellation scope and lifetime are made identical by construction. Because the controller cannot outlive the phase, there is no way to abort work that has not started, and no way for a previous cancellation to silently kill the next unit of work. Errors are reported live (`agent/error`) but re-thrown so the driver boundary — one place — decides containment.

*evidence:* packages/core/agent-loop/src/agent.ts:38-46, 99-140, 142-162, 210-223, 246-330; packages/core/agent/src/invariant.ts:15-24


**Two-list durable inbox (next-turn / next-step) + the wakeup boolean, and the followup/steer/inject triple**

One `Inbox` owns exactly two ordered lists keyed by `InboxTarget = 'next-turn' | 'next-step'` (agent/types.ts:10, inbox.ts:26). Every mutation is normalized to a splice `{target, start, removedCount?, inserted[], outcome?:'canceled'}` and APPENDED TO THE SESSION LOG as `agent/inbox/spliced` before the in-memory list mutates (inbox.ts:158-193) — so the inbox is a projection of the log, replayed on construction from the post-seed suffix (inbox.ts:32-39), and pending work survives a crash. Validation rejects out-of-range splices and duplicate message ids across BOTH lists (inbox.ts:203-219). `claim(target, turn)` is the step-boundary read: it drains ALL of next-step, and additionally shifts exactly ONE item off next-turn when `target === 'next-turn'` (inbox.ts:71-78) — that asymmetry is what makes a queued follow-up 'the sole ordinary message of its own turn' while injected context is batched.

The three public verbs are one primitive `send(message, target, wakeup)` with different (target, wakeup) pairs (agent.ts:113-132):
- `followup(m)` = ('next-turn', wake=true): a new user prompt. Solves 'the human said something new; it deserves its own turn'.
- `steer(m)` = ('next-step', wake=true): mid-flight redirection. Solves 'the human is talking while the model is working' — it must not wait for the whole turn to end, but it also must not interrupt an in-flight model call, so it lands at the NEXT step boundary. If idle, the wake starts a turn.
- `inject(m)` = ('next-step', wake=false): model-facing context from plugins (file-change notices, skill text, tool `additionalContexts`). Solves 'the model should see this the next time it is asked anything, but it is not a reason to think'. It piggybacks; if the agent stays idle it stays parked forever, which is correct.

The wakeup boolean is also a race fix. In `send`, `wakingAfterAbort = wakeup && phase.kind !== 'idle' && phase.abort.signal.aborted` is computed BEFORE the insertion, so a reentrant cancel triggered by a splice observer cannot reclassify the message; if the current activity is already aborted, the target is forced to 'next-turn' because waking input must not join a dying turn (agent.ts:113-119). `wakeDriver(wakeAfterAbort)` then either starts a driver (idle), or LATCHES `phase.wakeRequested = true` when the wake cannot be delivered now (maintenance, or an aborted-but-not-yet-converged driver) — never latching for a `disposed` cancel, so teardown does not wait on a new model turn (agent.ts:172-193). The latch is replayed at convergence in `kick`'s finally and in `runMaintenance`'s finally, but only `if (wakeRequested && inbox.hasPending)` — a wake whose message was cleared in the meantime is suppressed, while a wake that arrived while genuinely idle always opens its turn boundary even if the message is later removed (agent.ts:158, 219-221, 271-277).

`foldConsumedWork(events)` reads the same log to answer 'did this agent actually consume the work it was given?': a turn counts as accounting for its input if it reached `step/start`, or if it claimed inbox input and ended in a way that accounts for it (`blocked|aborted|error|interrupted` yes, `completed` no); `outcome:'canceled'` splices with nothing inserted mark work dropped unrun (consumed-work.ts:42-107).

*why:* Two lists, not one queue, because two different latencies are needed: turn-granular (a new goal) and step-granular (a correction / new context). The wakeup flag separates 'this is a reason to run' from 'this must be seen when you next run'. Durability of the inbox is what lets a crashed process resume without losing a user's queued prompt.

*evidence:* packages/core/agent/src/inbox.ts:26-39, 71-78, 139-219; packages/core/agent/src/types.ts:9-26; packages/core/agent-loop/src/agent.ts:113-132, 172-193; packages/core/agent/src/consumed-work.ts:42-107; packages/core/agent/src/runtime-types.ts:106-144


**turn/step boundaries: what is durable, what is live, what closes a turn, sticky max-tokens**

A STEP is one model request plus the tool calls it produced. A TURN is zero or more steps: opened before its first input is claimed, closed once nothing is owed (docs/architecture.md, 'Turn flow').

Durable (session events, survive reload): `turn/start`, `turn/end{reason}`, `step/start`, `step/end`, `user/message`, `assistant/chunk` (raw, per token), `assistant/message` (assembled, with `usage`, possibly `interrupted:true`), `tool/call`, `tool/result`, `request/header`, `request/context`, `agent/inbox/spliced`, `todo/write`, `session/end-seed`.
Live (Cordis events, never persisted): `agent/pre-step` (waterfall: `reject` | `enter(messages)`), `agent/request` (waterfall over the call config), `agent/request-error` (waterfall returning `{kind:'retry'}` or undefined), `agent/turn-stopping` (serial, no `next()`), `agent/status`, `agent/inbox/*`, `agent/error`, `llm/stream`, `tools/pre-execute|execute|post-execute`.

Turn body (agent.ts:246-330): append `turn/start{turn}`; loop { `preStep(target,{turn,step})` -> if `reject` set `turnEnds={kind:'blocked'}` and return; if the FIRST claim rewrites to empty, set `{kind:'completed'}` and return — a turn that spent no step is still a durable turn, so the log records the attempt; else append `step/start`, append every entered message as `user/message` with `surfaceOp:'append'`, run `step()`, and append `step/end` in a `finally` so a step is never left open; then, if the turn has an ending AND `inbox.nextStep` is empty, dispatch `agent/turn-stopping` (a listener may `agent.steer(...)` to force another step), re-check, and break; otherwise set `target='next-step'` and loop }. `turn/end{turn, reason}` is appended in the outer `finally` — every exit path (normal, aborted, errored) assigns a reason first. Structured errors: an `LlmError` keeps its `failure` verbatim, anything else flattens to `{message: errorChain(error), code:'UNKNOWN'}`.

So a turn closes when: pre-step rejected (blocked); first claim empty (completed); the model produced no tool calls (completed); a tool result carried `concludesTurn` (completed); max output tokens hit (max-tokens); abort; error — and in every non-reject case only after `agent/turn-stopping` has had its say and next-step is still empty.

MAX-TOKENS STICKINESS: `if (turnEnds === null || turnEnds.kind !== 'max-tokens') turnEnds = stepEnd` (agent.ts:290). Once any step in the turn hit the ceiling, a later normally-completing step (e.g. a continuation plugin steered another step) must not downgrade the turn's recorded outcome. `step()` returns `null` to mean 'tools ran, another request is owed' — `null` does not close the turn.

Step body (agent.ts:332-420): build the frozen request from `session.deriveMessages()`; stream; append EVERY chunk as `assistant/chunk` and collect their seqs; on abort, if any blocks were assembled, append the partial `assistant/message` with `interrupted:true` citing those chunk seqs; on a stream-level failure, offer `agent/request-error` a retry (`continue` re-enters the while loop and rebuilds the request); on success append the assembled `assistant/message` citing `sourceEventSeqs: chunkSeqs`; if `finish.kind === 'max-tokens'` return; else if no tool-call blocks return completed; else run `executeToolCalls`, whose `additionalContexts` are fed back with `inbox.splice('next-step', ...)` so tool-produced context enters the NEXT step's claim.

*why:* The turn/step split separates 'a unit of user-visible work' from 'a unit of model computation'. Durable-vs-live is the reload contract: anything a reader must have to reconstruct the conversation is an event; anything that only shapes the current execution is a live hook. Stickiness exists because the turn's reason is consumed by policy (continuation, UI, telemetry) and must describe the whole turn, not just its last step.

*evidence:* packages/core/agent-loop/src/agent.ts:246-330 (turn), 332-420 (step), 290 (sticky max-tokens), 291-293 (step/end in finally), 316-322 (turn/end in finally); packages/core/session/src/types.ts:236-337 (event map), 152-177 (TurnEndReason); docs/architecture.md 'Turn flow'


**The append-only SessionEvent log: contiguous seq, snapshot-on-append, deep freeze, publish-before-push**

`SessionEvent = {type, seq, time, data, ignorable?} (+ surfaceOp/sourceEventSeqs only on the three surface types)` — a discriminated union over `type` (session/types.ts:408-440). Contract: `seq === log.length` at append, so seqs are contiguous from 0 and double as array indices (index.ts:'The next event's sequence number — always the log length'). `append(type, data, opts)` (index.ts:604-655): (1) `snapshotJsonValue(data)` — one recursive pass that reads, validates and copies each nested value ONCE, so a stateful getter cannot hand one value to validation and another to storage; non-JSON data (BigInt, Date, Map, function, -0, NaN, circular, sparse) is rejected AT THE APPEND SITE, not later at flush; (2) reentrancy guard — an append inside another append's publication throws; (3) build the event, `deepFreeze` it; (4) `surfaceManager.validateNext(event)` — plans the surface transition WITHOUT mutating, so a rejected event cannot half-apply; (5) collect `session/event` listeners, THEN `log.push`, THEN invoke listeners. Listener failures are contained per listener and cannot un-commit the event. `events` returns a frozen snapshot array cached until the next append, so a previously returned array never grows under a holder.

Relational well-formedness is enforced by an optional companion (session/invariant.ts) that keeps a per-session trace `{lastSeq, openTurn, openStep, nextTurn, nextStep, pendingCalls}` and validates each candidate at `internal/dispatch` (pre-commit) then applies the transition at `session/event` (post-commit): seq strictly increases; no nested turns; `turn/end` matches the open turn and requires no open step; `step/start` must be exactly `nextStep`; chunk/message/call/result must name the open turn+step; a `tool/result` must have a prior `tool/call` in the same step (except the synthetic TOOL_NOT_STARTED recovery result); `request/header`, `request/context`, `todo/write` must be turn-enclosed.

Crash recovery is a pure function over the log: `interruptedTurnClosers(events)` returns the deterministic synthetic events (error results for unmatched calls, then `step/end`, then `turn/end{kind:'interrupted'}`) needed to make a crash tail into a provider-valid transcript, continuing the seq numbering and reusing the last real timestamp (repair.ts:27+).

*why:* The log is the single source of truth for everything — resume, fork, transcripts, telemetry, token accounting, UI replay. Making it append-only, contiguous, frozen, and JSON-lossless means a reader anywhere (another process, a UI, an offline analyzer) reconstructs exactly what the runtime had, and a bad write fails loudly at its origin instead of corrupting durable history.

*evidence:* packages/core/session/src/index.ts:559-566 (events snapshot), 604-655 (append), 526-541 (seed acceptance); packages/core/session/src/types.ts:230-440; packages/core/session/src/invariant.ts:55-166, 223-241; packages/core/session/src/repair.ts:12-70


**The 'surface': an ordered view over the log that decides what the model sees**

Only three event types are surface-eligible: `user/message`, `assistant/message`, `tool/result` (types.ts:347-351). Every append of one of those MUST carry a `surfaceOp` — the compiler requires it (`opts` is conditional on `T extends SurfaceEventType`) and the runtime re-checks it; a non-eligible event carrying `surfaceOp`/`sourceEventSeqs` is rejected (surface.ts:185-208). `surfaceOp` is either `'append'` (join the tail) or `{op:'replace', start, end}` (both must be CURRENT surface nodes; replaces the inclusive index range with this one node). `sourceEventSeqs` is provenance: every cited seq must be a distinct earlier event, and for a replace it must INCLUDE EVERY SHADOWED NODE (surface.ts:210-243). `assistant/message` may cite an empty array (known-empty provider stream).

The fold state is `{nodes: number[], replaceGeneration: number}`. Append pushes the seq; replace does `nodes.splice(startIdx, endIdx-startIdx+1, thisSeq)` and increments `replaceGeneration` (surface.ts:362-379). `foldSurface(events)` is the pure offline replay; `SurfaceManager` is the live incremental one — it lazily folds only the delta since the last read, and `validateNext(event)` pre-plans the pending event so acceptance and commit are the same code path (surface.ts:387-459).

Extra rule for tool results: a `tool/result` replacement must shadow exactly ONE current node, which must itself be a `tool/result`, and may differ ONLY in message content — everything else (callId, turn, step, error, meta) must be deep-equal (surface.ts:286-318). That is what lets a pruner shrink a huge tool output without breaking call/result pairing.

`deriveEventMessage(event)` is THE per-node projection rule (surface.ts:83-114): `user/message -> event.data` verbatim (no re-added framing — framing is baked into content by the producer), `assistant/message -> event.data.message` unless its content is empty (a max-tokens step's usage-only carrier, which must not inject a content-less assistant turn), `tool/result -> event.data.message`, everything else -> null.

*why:* It decouples 'what happened' (the log, immutable, complete) from 'what the model is shown' (an ordered subset that can be rewritten). Two readers with different needs are served without forking storage: the model reads the surface; a human transcript reads only `isAppendSurfaceEvent` nodes, because the surface deliberately shadows replaced ranges and would otherwise erase conversation the user already saw (surface.ts:40-55).

*evidence:* packages/core/session/src/surface.ts:14-114, 184-243, 286-379, 397-459; packages/core/session/src/types.ts:342-393


**deriveMessages(): incremental projection with replaceGeneration invalidation**

Three fields of cache state: `derived: Message[]`, `derivedNodes` (how many surface nodes are already projected), `derivedGeneration` (the `replaceGeneration` the cache was built under) (index.ts:702-706). `deriveMessages()` (index.ts:726-751): read `surface.nodes` and `surface.replaceGeneration`; if the generation differs, THROW THE WHOLE CACHE AWAY (`derived=[]; derivedNodes=0; derivedGeneration=generation`); then project only `nodes.slice(derivedNodes)` through `deriveEventMessage`, skipping nulls; return `[...derived]` — a fresh array each call so a later append never grows an array a caller already holds, while the `Message` objects inside are SHARED and deep-frozen (they reuse the already-frozen durable event data, so no second deep clone is needed and no consumer can mutate the log).

Cost: O(new nodes) per step in the common append-only case; O(surface) exactly once after a compaction. The whole-cache-rebuild-on-replace is deliberate: a positional splice can move or delete arbitrarily many nodes, so an incremental patch would need per-node bookkeeping that the monotonic generation counter replaces with one integer compare.

*why:* Every step calls it (`this.session.deriveMessages()` is the request's message array) and the request invariant calls it again to verify — it must be cheap and it must be EXACT. A generation counter makes correctness after a rewrite trivially provable instead of depending on splice-patching logic.

*evidence:* packages/core/session/src/index.ts:702-751; packages/core/agent-loop/src/agent.ts:341; packages/core/agent-loop/src/invariant.ts:39-42


**Compaction: rewriting history without mutating the log (surfaceOp replace + sourceEventSeqs)**

Nothing is ever deleted. A compactor appends NEW events that shadow old surface positions.
Summarizing compaction (compaction-basic/region.ts): open a bracket `compaction/start{compactionId, turn}`; summarize the selected span (an LLM call of its own); re-check stability (`assertWholeSurfaceUnchanged` or `assertSelectedSpanStable`) because the surface may have moved during the async summarization, and abort with a `SurfaceChangedError` if it did; append `compaction/summary{shadowedRange, shadowedSeqs, shadowedTokenCount, provider, model, usage, rawOutput}` (log-only, not on the surface); then append the checkpoint as `user/message` with `surfaceOp:{op:'replace', start, end}` and `sourceEventSeqs:[startEvent.seq, summaryEvent.seq, ...shadowedSeqs]`; close with `compaction/end`. Failure appends `compaction/end{error}` so the bracket is always balanced.
Pruning compaction (compaction-tool-result-pruner): append `compaction/prune{shadowedRange, shadowedSeqs, shadowedTokenCount}`, then re-append the same `tool/result` with truncated content under `surfaceOp:{op:'replace', start:seq, end:seq}, sourceEventSeqs:[seq]` — allowed precisely because the content-only rewrite rule (surface.ts:286-318) holds.

Effect: `surface.nodes` shrinks, `replaceGeneration` bumps, `deriveMessages()` rebuilds and the model now sees the summary instead of the span. The original events are still in the log at their original seqs with their original bytes — so the human transcript, telemetry, token accounting, and any later forensic read are unaffected. `session.fork(source, boundary)` can still cut at any seq boundary (rejected only if the prefix ends inside an open turn).

A consumer that cares whether its own contribution was compacted away watches for it: `RuntimeContextProjection` listens for `isReplacementSurfaceEvent(event) && event.sourceEventSeqs?.includes(this.retained.seq)` and drops its retained state (runtime-context.ts:46-55).

*why:* Context windows are finite but history is evidence. Replace-by-append gets both: a bounded model-visible surface and a complete immutable record, with provenance (`sourceEventSeqs`) making the rewrite auditable and reversible by re-derivation from any log prefix.

*evidence:* packages/compaction/compaction-basic/src/region.ts:183-229, 447-465; packages/compaction/compaction-tool-result-pruner/src/index.ts:161-176; packages/core/session/src/surface.ts:245-266, 286-318, 362-379; packages/core/agent-loop/src/runtime-context.ts:46-55


**The 'model-visible IFF logged' invariant, enforced at runtime in agent-loop/invariant.ts**

Stated in docs/architecture.md: 'Model-visible means logged. Anything that reaches a model request must be reconstructable from the log, and a runtime invariant asserts it.' Enforcement (agent-loop/src/invariant.ts:19-55): a listener on the `llm/stream` waterfall registered `{global: true, prepend: true}` — PREPEND so a short-circuiting replay/mock listener cannot silence the check. It ignores requests not marked by `markAgentLoopRequest` (a process-local WeakSet identity, call-config.ts:12-13, 66-78 — so identity cannot be forged by shape). For a loop-built request it asserts:
1. `Object.isFrozen(options)` and `Object.isFrozen(options.messages)` — the request was deep-frozen (deepFreeze deliberately skips AbortSignal so abort still works).
2. `options.sessionId !== undefined` and resolves to a LIVE session.
3. the session log contains at least one `step/start`.
4. `foldRequestHeader(session.events)` yields a header (a `request/header` event exists).
5. **`JSON.stringify(options.messages) === JSON.stringify(session.deriveMessages())`** — the outgoing message array is byte-identical to the independent re-derivation from the durable log. This is the actual teeth: any content injected into the request that was not appended as a surface event fails here.
6. every header field matches the folded header: `model`, `system`, `temperature`, `maxTokens`, `stop`, `tools`.
`fail(msg)` throws an `InvariantError` (invariants/src/index.ts:29, 162), and because the listener is prepended on the waterfall, the throw happens BEFORE the provider call — a desync aborts the request rather than shipping unreconstructable context. The whole invariants service is an opt-in diagnostics companion (`ctx.invariants.register(PACKAGE_NAME, install)`), so production can run without the double derivation cost while dev/CI runs with it.

*why:* Without it, the log slowly becomes a lie: a plugin appends context straight into the request, and the session can no longer be resumed, forked, replayed, or token-accounted correctly — silently. The check turns a class of subtle drift bugs into a loud, localized failure at the exact dispatch that caused it. It is also the architectural forcing function: 'a new model-visible input requires a new session event.'

*evidence:* packages/core/agent-loop/src/invariant.ts:19-55; packages/llm/llm/src/call-config.ts:12-13, 61-78, 80-115; packages/runtime-diagnostics/invariants/src/index.ts:25-39, 136-191; docs/architecture.md 'Session log'


**Request-header folding: diff-and-append-on-change, plus adapterDefaults**

`EpochHeader = {config: LlmCallConfig, adapterDefaults?, system?, tools?}` — the per-request state that is NOT message history (types.ts:196-210). It is stored as full snapshots in `request/header` events; there is no delta format (a legacy `request/header-delta` is explicitly rejected at load, index.ts:213-216).

Per step, `buildRequest` (agent.ts:426-514):
1. Seed the proposal. FIRST request of this loop instance: from the declared route `{provider, model}` + `maxTokens` from options, restoring a persisted `reasoningEffort` ONLY if the persisted config names the exact same provider+model AND the persisted header did not mark that field adapter-derived. LATER requests: `requestProposal(persistedHeader)` — the last logged config with every field flagged in `adapterDefaults` DELETED (agent.ts:54-61), so an adapter-resolved default is re-resolved instead of being frozen in as if the user had chosen it.
2. `deepFreeze(structuredClone(seed))`, then run the `agent/request` waterfall so plugins can rewrite the config (model downgrade, effort selection, etc.). Missing provider/model is a hard error.
3. `llm.prepareCall(config)` returns the adapter-resolved `config` plus `adapterDefaults` marking which fields the adapter supplied; a `NO_ADAPTER` error is tolerated (middleware may serve an unregistered route) and the proposal is used as-is.
4. `canonicalHeader({config, adapterDefaults, system, tools})` normalizes: an empty system prompt and an empty tool list become ABSENT fields, matching how requests are actually built (request-header.ts:21-31). One representation for logging, folding and comparison.
5. Diff and append: if this loop instance has not yet logged a header, append one with `reason: baseline === undefined ? 'initial' : 'resume'` (so a restart or fork re-anchors); otherwise append `reason:'change'` ONLY when `!headerEquals(baseline, header)` (agent.ts:483-489). `headerEquals` is field-wise: `callConfigEquals` on config, both adapterDefaults flags, `system` string identity, and tool schemas compared in order by canonical JSON (request-header.ts:33-54).
6. `request/context` (provider, model, contextWindow) is logged separately and only on change; it deliberately does NOT participate in header equality or request reconstruction (agent.ts:491-502, types.ts:309-313).
7. The actual request is `markAgentLoopRequest(deepFreeze({...header.config, messages: boundaryMessages, system?, tools?, sessionId, signal}))` — i.e. built FROM the header that was just logged, never from the local variables that produced it.

Reconstruction: `foldRequestHeader(events, from?)` takes the last `request/header` and canonicalizes it; the live `Session.requestHeader()` maintains the same fold incrementally (fold once per new event, cached at `headerFoldSeq`, deep-frozen because it is exposed by reference) (index.ts:657-680, request-header.ts:65-71).

*why:* System prompts and tool schemas are large and mostly constant; logging one per step would dominate the log and destroy prompt-cache reasoning. Folding gives O(1) 'what header was in force at seq N' for any reader, and appending only on change makes header churn (a model switch, a tool set change) explicit and auditable. `adapterDefaults` exists so that 'the adapter picked this' never masquerades as 'the caller asked for this' and get pinned forever across model switches.

*evidence:* packages/core/agent-loop/src/agent.ts:54-61, 426-514; packages/core/session/src/request-header.ts:21-71; packages/core/session/src/types.ts:196-228; packages/llm/llm/src/call-config.ts:17-59; packages/core/session/src/index.ts:657-680


**RuntimeContextProjection: making a re-rendered dynamic context snapshot idempotent on the log**

Dynamic context (cwd, git state, open files, time — the things that change between steps) is rendered fresh at every pre-step by `systemPrompt.assemble` + `renderContextSections`. Naively appending it every step would append a near-identical `user/message` per step. `RuntimeContextProjection` (runtime-context.ts:25-76) keeps `retained: {seq, text} | null | undefined` — `undefined` = no snapshot ever existed, `null` = none retained. On construction it scans the log BACKWARDS for the last `user/message` owned by the system-prompt plugin (`source.kind === 'plugin' && source.plugin === SOURCE`) that is STILL a live surface node (`session.surface.nodes` set membership) — a snapshot compacted away is correctly treated as gone. It then follows `session/event` to stay current, and drops the retained state when a replacement surface event cites its seq.
`project(current, sections)` returns a candidate `UserMessage` only when the rendered text actually DIFFERS from the retained one; an emptied context renders the explicit sentinel 'Current runtime context: none. Earlier runtime-context snapshots no longer apply.' rather than silently vanishing. `preStep` appends the candidate to the claimed batch (agent.ts:232-240), and the turn loop is what actually commits it via `session.append('user/message', ..., {surfaceOp:'append'})` — the projection never writes to the log itself.

*why:* It is the reference pattern for high-frequency observations under a 'model-visible IFF logged' regime: dedupe against the last LOGGED value, emit an explicit invalidation marker instead of an implicit disappearance, and re-derive retention from the surface so compaction is respected. This is the single most directly transferable mechanism for a robot's state observations.

*evidence:* packages/core/agent-loop/src/runtime-context.ts:12-76; packages/core/agent-loop/src/agent.ts:225-243, 282-284


**Tool-call scheduling: exclusive barriers, bounded parallel pool, model-order commit, synthetic results on abort**

`executeToolCalls` (tool-calls.ts:59-101) parses each call's arguments (invalid JSON is preserved as raw text, empty becomes `{}`), then walks the call list in model order. It asks the registry for each call's LIVE execution mode; a `parallel` head takes the whole remaining slice as a group, anything else is a group of one (a barrier). Inside a group (tool-calls.ts:121-246): a rolling pool bounded by `maxParallelToolCalls` (default 10, read fresh per group so a config change caps the next group without disturbing the one in flight); each start appends `tool/call` and REMEMBERS ITS SEQ so the eventual `tool/result` can cite it in `sourceEventSeqs`; dispatch may overlap, but `commitReady()` advances `committed` only across CONTIGUOUS model-order slots, so results, `tools/post-execute` finalization, and `additionalContexts` all commit in model order regardless of completion order. Later calls are re-classified before starting, so a registry change mid-group can create a barrier. On abort: stop starting, drain what started, commit their results and contexts, then append a synthetic `tool/call` + error `tool/result` (`TOOL_ABORTED_BEFORE_DISPATCH`) for every call that never ran — so the durable transcript keeps every call paired with a result and stays provider-valid on replay. A scheduler-internal failure is different: it stops new dispatches, drains started ones, and rethrows WITHOUT fabricating results. Any result with `concludesTurn` makes the step return `{kind:'completed'}`.

*why:* Providers reject a transcript with an unmatched tool call, so 'every call has a result' is a durability invariant, not a nicety. Model-order commit keeps the log deterministic and replayable even though execution is concurrent.

*evidence:* packages/core/agent-loop/src/tool-calls.ts:59-101, 121-246, 248-289; packages/core/agent-loop/src/constants.ts:6; packages/core/agent-loop/src/agent.ts:412-418

Embodied mapping: this is the episode/rosbag log, but with the crucial difference that it is also the AGENT'S OWN STATE — the policy's message history is derived from it rather than kept beside it.

Embodied mapping: log every observation at control frequency (200 Hz IMU, 30 Hz RGBD, every torque command) as non-surface events; put only decision-relevant items on the surface (a keyframe observation, a skill invocation, a skill result, an operator utterance). `{op:'replace', start, end}` + full `sourceEventSeqs` then lets a downsampler collapse 300 logged frames into one summarized 'state at t' node WITHOUT deleting the frames — the replay/training pipeline still sees all 300. Adopt the content-only rewrite rule for skill results (surface.ts:286-318): a pruner may shrink a point cloud attached to a skill result but may not change its call id, so pairing survives.

This is what makes 'derive the policy's context from the log every single step' affordable at decision frequency. Return a fresh list of shared frozen objects.

Reimplement as a hook on the policy-invocation seam that, for harness-built requests only (identity via a `WeakSet`/`id()` registry, never by shape), re-derives the observation/message context from the log and compares it to what is about to be sent, plus compares the folded header. Make it a registrable diagnostics companion that CI and sim runs enable and the robot can disable. Embodied mapping: this catches the single most damaging class of robotics-agent bug — a perception node or a safety wrapper slipping context into the policy call that never entered the log, making the episode non-replayable and every offline eval subtly wrong.
- HEADER FOLDING WITH DIFF-AND-APPEND-ON-CHANGE + adapterDefaults. Embodied mapping: the 'header' is the episode's non-observation configuration — policy checkpoint id, control mode, gains, safety envelope, speed scaling, active skill schemas, calibration id. Snapshot it, canonicalize it (empty -> absent), append it only when it actually differs, and mark which fields the DRIVER resolved rather than the operator (`adapterDefaults` -> `driver_defaults`), so a re-resolved gain is not frozen in as an operator choice across a controller swap. `fold_header(events)` then answers 'what config was in force at seq N' for any offline reader, which is exactly what a post-incident analysis needs.
- RUNTIME-CONTEXT PROJECTION AS THE HIGH-FREQUENCY-OBSERVATION PATTERN. This is the direct answer to 'observations at control frequency vs. an append-only log': render the state snapshot every step, but only append when the rendered value CHANGED from the last one still live on the surface; emit an explicit 'no state retained' sentinel instead of letting it silently vanish; recover retention state by scanning backwards for the last owned node that is still a surface member; and drop retention when a replacement cites its seq. Extend it for robotics with a change threshold (norm distance / quantization) and a max staleness interval, since floats never repeat exactly.
- MODEL-ORDER COMMIT WITH A BOUNDED CONCURRENCY POOL AND SYNTHETIC RESULTS ON ABORT. Embodied mapping: skills/actions dispatched concurrently (start the arm, keep the base servoing) but committed to the log in decision order, with exclusive skills acting as barriers (anything that moves the base, anything that changes the tool). On e-stop: drain what started, commit their real outcomes, then append a synthetic 'aborted before dispatch' result for every unstarted action so the log never contains an action with no outcome. Re-read the concurrency cap per group so a config change caps the next group, not the one in flight.
- CRASH REPAIR AS A PURE FUNCTION OVER THE LOG. `interrupted_turn_closers(events) -> list[Event]`: synthesize outcome records for unmatched actions, then `step/end`, then `episode/end{kind:'interrupted'}`, continuing the seq numbering and reusing the last real timestamp. Embodied mapping: a robot that loses power mid-motion is the NORMAL case, and boot must turn a torn log into a well-formed one deterministically before the policy ever sees it.
- CONSUMED-WORK FOLD. `fold_consumed_work(events)` answering 'did the robot actually act on the task it was given, or was it dropped unrun?' from the log alone, with `outcome:'canceled'` splices distinguishing 'cancelled before it ever ran' from 'ran and failed'. Embodied mapping: this is the task-accounting/acknowledgement contract a fleet scheduler needs, and deriving it from the log means any cancel path — operator, supervisor, watchdog, shutdown — reads the same.
- STEP/EPISODE BOUNDARY DISCIPLINE: open marker appended before any input is claimed; close marker appended in a `finally` on every exit path with a structured reason; inner step markers also closed in a `finally`; a stopping hook (`agent/turn-stopping`, serial, no next()) consulted before the episode is allowed to close, with the hook able to enqueue more work and force another step. Plus stickiness: a degraded outcome (dsh's max-tokens; a robot's `torque-limited`, `envelope-clamped`, `perception-degraded`) recorded by any step must not be downgraded by a later clean step.

**ANTIPATTERNS**
- DO NOT log every observation as a SURFACE event. dsh gets away with 'every model-visible input is a session event' because chat inputs are rare and human-paced. At 30-200 Hz, `surface.nodes` becomes a million-entry list, `deriveMessages()`'s O(new nodes) tail projection is fine but the O(surface) rebuild after every downsample/compaction is not, and `JSON.stringify(messages)` in the request invariant (invariant.ts:40) becomes an unaffordable per-step cost. Split the invariant: log everything, but let only keyframes/decision-relevant nodes on the surface, and verify by content hash rather than JSON string comparison.
- DO NOT copy `snapshotJsonValue` + `deepFreeze` verbatim for sensor payloads. dsh's append does a full recursive JSON copy AND a full deep freeze of every event's data (index.ts:604-655) — correct for a few KB of text, catastrophic for images, point clouds, and tensors. Store large observations by reference (content-addressed blob id / rosbag offset) in the event, freeze only the small envelope, and keep the 'losslessly serializable' validation on the metadata.
- DO NOT make the append path synchronous-notify-then-return on a real-time thread. dsh appends and synchronously invokes every `session/event` listener inside the append call, containing failures per listener. That is the right SEMANTICS but the wrong THREADING for a control loop: a slow subscriber would stall the controller. Keep the ordering guarantee (commit-then-publish) but publish to a bounded queue drained off the control thread, and make the queue's overflow policy explicit — dropping an event silently would break the 'reconstructable from the log' invariant that everything else rests on.
- DO NOT reuse `time: Date.now()` millisecond wall-clock as the only timestamp. dsh's events carry a single ms wall-clock field. A robot log needs monotonic time, and usually a hardware/controller timestamp distinct from the log-append time, plus a way to relate them. Retrofitting this later invalidates every offline consumer.
- DO NOT assume 'a turn is closed once nothing is owed' transfers to an episode. dsh's turn ends when the model stops asking for tools; there is no world that keeps changing while it is idle. An episode can be `completed` (goal reached), but it can also need to end on a timeout, an envelope violation, a battery threshold, or an operator preempt — none of which are 'the policy stopped asking'. Extend `TurnEndReason` (it is deliberately a merge-extensible map, types.ts:152-177) rather than forcing robot endings into `completed|error|aborted`.
- DO NOT port the 'aborted request logs nothing unless blocks were assembled' rule (agent.ts:354-370). In chat, an aborted request that produced no text legitimately leaves no `assistant/message`. In a robot, an aborted DECISION that already emitted a partial trajectory has physically happened; the log must record what was actually commanded, not what was assembled. The nearest correct analogue is dsh's synthetic `TOOL_ABORTED_BEFORE_DISPATCH` result — record the fact that it did not run, and separately record what did.
- DO NOT keep the `steer` semantics of 'lands at the NEXT step boundary' for safety-relevant input. dsh deliberately refuses to interrupt an in-flight model call; steering waits. An e-stop or a human-in-workspace alert must NOT wait for the current decision step — it must go through the cancel path (which aborts the phase signal immediately), not the inbox. Keep the inbox for non-urgent redirection and keep a separate, always-preemptive safety channel; conflating the two is how a 'steering' message ends up queued behind a 400 ms policy call.
- DO NOT port `RuntimeContextProjection`'s exact-string equality (`this.retained?.text === snapshot`, runtime-context.ts:67) to float state. Joint angles and poses essentially never repeat exactly, so a naive port appends a snapshot every single step — the opposite of the mechanism's purpose. It needs a tolerance/quantization policy and a max-staleness bound.
- DO NOT adopt the invariants companion as an always-on production check. It re-derives the full message history and stringifies it on EVERY request (invariant.ts:39-42). dsh makes this acceptable by making it an opt-in registrable companion. Run it in sim, CI, and replay; gate it off (or downgrade to a hash) on the robot.
- DO NOT copy the single global 'one open turn, one open step' relational trace (session/invariant.ts:23-30) into a multi-limb / multi-subsystem robot without generalizing it. dsh's model has exactly one thing happening at a time. If arm, base, and gripper skills genuinely run as independent concurrent tracks, a single `openStep` scalar will either reject legal logs or force artificial serialization; the tool-call scheduler's barrier/pool model (tool-calls.ts:121-246) is the right precedent for the concurrency, but the log trace needs per-track open/close state to match.
- DO NOT treat compaction's `assertStable` re-check as optional. `compactRegion` summarizes asynchronously and then re-verifies that the span it is about to replace has not moved (region.ts:190-192, 211). A robot's log grows during any async summarization, and a replace against stale indices would silently shadow the wrong nodes — `{op:'replace', start, end}` is POSITIONAL over current surface nodes, so this check is load-bearing, not defensive.

**SandboxProvider.confine() — argv-wrapping Service Definition, fail-closed by construction**

ctx.sandbox.confine(argv, policy) does not spawn anything itself; it returns a REPLACEMENT argv (runner + profile args + '--' + original argv) that the caller spawns instead of its own. Every implementation must either return enforcing argv or throw SandboxUnavailableError (code SANDBOX_UNAVAILABLE) — there is no code path that returns the original argv unconfined. Policy (SandboxPolicy: mode + workspaceRoot + optional sessionId) rides the call, not the provider, so two consumers can confine under different modes simultaneously.

*why:* Keeps the Service Definition dependency-light (only cordis + harness error base) and mechanism-agnostic across bwrap/Landlock/Seatbelt/ACL, while making 'silently ran the model's command unconfined' structurally impossible — the type signature only offers 'wrapped argv' or 'throw'.

**Platform runner chain: sole-candidate-vs-probed-chain selection**

PLATFORM_CHAINS maps linux -> ['bwrap','landlock'], darwin -> ['seatbelt'], win32 -> ['windows-acl']. A chain of length 1 (darwin, win32) is selected WITHOUT any functional probe — its own execution-time refusal is the fail-closed end. A chain of length >1 (linux) is walked in preference order, each rung functionally probed once (spawn the real read-only profile around `true` and check exit 0), and the verdict is cached for the provider's lifetime.

*why:* Probing arbitrates between competing candidates; it doesn't re-validate a choice that has no alternative. Caching means a broken/repaired runner requires a plugin reload, not a rediscovered constant per call — the exact reusable lesson for a Python daemon: pay the discovery/probe cost once per process lifetime, never per request.

*evidence:* packages/sandbox/sandbox-local/src/index.ts:159-165 (PLATFORM_CHAINS), :487-506 (chainVerdict, selectRunner caching), :74-91 (defaultProbeSeatbelt — spawns real read-only profile around `true`)


**Seatbelt profile: allow-default + deny-file-write* + literal/subpath allow-lists**

seatbeltProfileArgs() builds SBPL: '(version 1)(allow default)(deny file-write*)' plus an explicit '/dev/null' literal allow, plus (under workspace-write) a subpath allow over writableRoots() — the canonicalized (realpath-resolved) union of {workspaceRoot, /tmp, os.tmpdir()}. This is passed as `sandbox-exec -p '<profile>' -- <argv>`.

*why:* Everything EXCEPT file writes stays default-allowed (network, process spawn, reads) — the vocabulary is deliberately file-effects-only (documented limitation: 'the seam expresses no network, process, syscall, device, or credential restrictions'). Canonicalizing roots matters concretely: Seatbelt matches resolved paths, so '/tmp' must be expressed as '/private/tmp' on Darwin or the allow-list matches nothing. The same writableRoots() helper feeds both the Seatbelt grant and the in-process fs fence so the two enforcement layers can't drift into different definitions of 'workspace-write'.

**Enforcement completeness is reported, never assumed 'full'**

ConfinedArgv carries `enforcement: 'full' | 'partial'` alongside the wrapped argv. bwrap/Landlock(full-ABI)/Seatbelt claim 'full' because their profiles govern every promised file effect by construction; windows-acl always reports 'partial' because WRITE_RESTRICTED must retain Everyone for process init and NTFS hard links can alias a granted path — a documented, structural gap the provider refuses to overstate as full.

*why:* Callers requiring an absolute boundary must be able to distinguish a real guarantee from a best-effort one instead of trusting a boolean 'sandboxed: true'.

**Denial dialect vs runner-failure dialect — two distinct stderr classifiers, never conflated**

Every wrap also returns `denialSignatures` (the case-insensitive substrings THIS backend's kernel produces when it denies a file effect — 'read-only file system' for bwrap, 'permission denied' for Landlock, 'operation not permitted' for Seatbelt) and `runnerFailureRules` (structured evidence — allowedExitCodes + fatalSignatures + informationalLines — that the RUNNER itself refused to start, meaning the command never ran at all). A consumer applies allowedExitCodes first, strips informationalLines by exact match, then matches fatalSignatures — only then may it fall back to denialSignatures.

*why:* 'Exit status alone never proves runner failure' — a confined child that deliberately mimics the runner's own failure text on stderr could otherwise be misclassified. Separating the two channels means a consumer never confuses 'confinement worked and blocked the command' with 'confinement itself never engaged.'

**CodeRunResult.error is a FIELD, never a rejection — the orthogonal CodeRunFailure taxonomy**

CodeRuntime.run(request) always RESOLVES (never rejects) for every program outcome. The six-way `kind` union — exception (thrown/parse failure), timeout (budget expiry), abort (caller signal fired), worker-exit (substrate died, e.g. OOM), invalid-output (completion not lossless JSON), output-limit (serialized output over cap) — are reported as independent, non-overlapping outcomes on a resolved CodeRunResult, never as a caught exception from run(). run() only REJECTS for Service Definition contract misuse (e.g. calling run() after the runtime disposed, or an invalid binding namespace name) — misuse of the API, not anything the model's program did.

*why:* Keeps 'the program failed' and 'the caller misused the seam' as structurally distinct error channels, so a consumer (Code Mode) can always treat run()'s resolution as 'the complete, safe-to-render outcome' without a try/catch around program execution — the taxonomy's job is to let the model self-correct from result.error.message rather than an opaque exception.

*evidence:* packages/code-runtime/code-runtime/src/types.ts:79-107 (CodeRunFailure kind union + doc), :111-124 (CodeRunResult, 'error is a FIELD on a resolved result, never a rejection')


**Two independent, orthogonal budgets: measured busy-time vs wall-clock backstop**

computeMs (default 60s) meters the worker's MEASURED event-loop active time via worker.performance.eventLoopUtilization(), polled every ELU_POLL_INTERVAL_MS=25ms (a fixed internal cadence, not config) — a hot synchronous loop expires this no matter what's dispatched, and a program idling on a slow tool call accrues zero busy time. maxWallMs (default 600s, hard-capped at MAX_TIMER_DELAY_MS because Node clamps a longer setTimeout to 1ms) is a plain setTimeout that 'never pauses for anything' — the backstop for what busy-time metering cannot see (awaiting a promise nobody will ever resolve). Either firing calls the same `finish()` path, which calls worker.terminate() (kills even a hot synchronous loop) and awaits stdout/stderr pipe drain before resolving. Heap overflow is NOT proactively capped by either timer — resourceLimits.maxOldGenerationSizeMb makes V8 itself OOM-kill the worker, surfacing asynchronously as the 'worker-exit' kind via the worker's own 'exit' event.

*why:* A single wall-clock timeout can't distinguish 'genuinely compute-bound' from 'idling on a slow tool' fairly, and can't be gamed by keeping a decoy call in flight; busy-time metering alone can't catch a program that awaits forever. Two independent budgets close both gaps without either budget being adversarially exploitable by 'hostile peer' program code.

**'Containment, not a security boundary' — explicit, load-bearing trust-posture split**

The worker-thread backend's own README states model code inside it has 'bash-equivalent trust' — it gets an empty environment (env:{}, stronger than the scrubbed-env rule for spawned commands) and no inherited loader flags (execArgv:[]), a capped V8 heap, and hard termination on budget expiry, but it is explicitly NOT a kernel-enforced filesystem/network/process boundary the way ctx.sandbox.confine() is. The README's Known Limitations section says outright: 'Only the worker-thread backend ships — a hard security boundary awaits a container backend.'

*why:* Names the actual tradeoff instead of hiding it: a fresh worker_threads.Worker per run gives cheap, fast, isolate-per-run containment (no cross-run state, hard-killable, heap-capped) at the cost of NOT confining what the program can reach at the OS level (network, filesystem outside the JS realm, subprocess spawning are all still bash-equivalent). This is precisely why the sandbox seam (ctx.sandbox) and the code-runtime seam (ctx.codeRuntime) are two separate capability seams rather than one — they trade off latency/cost against confinement strength differently and are composed, not merged.

**Nested tool calls from model-written programs re-enter the FULL guarded pipeline, not a shortcut**

code-mode.ts's `binding(name)` closure, invoked when the program calls `await tools.someName(args)`, does not execute the tool directly. It pushes a PendingDispatch onto an ordered driver queue and calls `registry[TOOL_RUNTIME_SCHEDULER].prepare(input)` then `.dispatch(prepared.exec)` then (in commit()) `.finalize(...)`/`.finish(...)` — the EXACT SAME four scheduler methods (prepare/dispatch/finalize/finish) that back the registry's ordinary top-level `execute()` path used by the native agent loop for model-issued tool calls. `prepare()` runs the full `tools/pre-execute` waterfall (hooks, permission, sandbox-mode denial via bash-sandbox's ctx.sandbox.confine()) plus registered monotonic guards BEFORE anything executes; `dispatch()` runs the `tools/execute` waterfall (timeout/retry/metrics wrapping) around the tool body; `finalize()` runs `tools/post-execute` and content finalization. A denial anywhere in that pipeline surfaces to the program as an ordinary JS exception thrown from the awaited binding call (`if (outcome.isError) throw new Error(outcome.message)`), which the program can catch like any other rejection.

*why:* The registry is designed for exactly this reuse ('Symbol-keyed scheduler view that keeps pre/post policy ordered while overlapping dispatch') so that policy — sandbox mode, approval gates, hooks, per-tool guards — has exactly one enforcement point regardless of whether a call originated as a top-level model tool-call or as a nested dispatch from inside a run_code program. There is no separate, weaker code path for programmatic sub-calls: 'Enforce a decision in the operation that makes it... test denial through the executor' (packages/CLAUDE.md) is upheld structurally rather than by convention.

**tools/pre-execute -> guards -> tools/execute -> tools/post-execute waterfall stages and their purpose**

Per the pipeline doc: (1) `tool/call` is logged BEFORE execution and the UI pending card renders (presentCall). (2) `tools/pre-execute` waterfall runs hooks + permission + sandbox-adjacent policy and can allow/deny/ask; an `ask` resolves through ctx.approval (one-shot prompt; absent or unanswerable = deny). (3) Registered monotonic guards run after pre-execute and can only deny or abstain (never override an approved allow) — this is where 'identity protected' invariants live. (4) `tools/execute` waterfall wraps the actual `execute()` body for around-dispatch concerns like timeout/retry/metrics; the tool body itself may append tool-owned session events (fs/observed, tool/code-dispatch, etc.) and — for tool-fs — pass through an `fs/write-intent`/`fs/edit-intent` gate before the body runs. (5) `tools/post-execute` waterfall can accept/block/replace the result or add context, running on BOTH tool-body results and pre-execute/guard denials (post always runs; denied calls skip only the body). (6) The registry losslessly snapshots the result, throws become isError via normalization, `finalizeContent` applies the tool definition's own last content-only transform, then the frozen `tools/result` notification fires synchronously before the session event and UI presentResult.

*why:* Each stage has one job and a hard ordering guarantee: pre-execute/guards decide IF the body runs at all (fail-closed on any throw -> normalized isError, never silently allowed), tools/execute wraps HOW it runs (timeouts etc.) without being able to skip the decision already made, and post-execute can only reshape an already-produced result, never retroactively decide whether it should have run. This lets cross-cutting policy (hooks, approval, sandbox mode) live outside individual tools while guaranteeing no call — top-level or nested via Code Mode — can bypass it.

*evidence:* docs/tool-execution-pipeline.md (full mermaid flow + prose), packages/core/tools/src/index.ts:152-176 (tools/pre-execute, tools/execute, tools/post-execute waterfall event signatures)


**REUSABLE**
- Split isolation into two seams with an explicit, documented trust gradient, exactly like ctx.sandbox (kernel-enforced, per-invocation, coarse-grained, fail-closed) vs ctx.codeRuntime (in-process containment, cheap, fast, explicitly NOT a security boundary). For a Python macOS critic-runtime this maps to: (A) a sandbox-exec-wrapped SESSION/EPISODE-lifetime confined worker process for the real OS-level file/no-network boundary, probed and cached ONCE (mirroring sandbox-local's chainVerdict caching for the provider's lifetime), and (B) a fast, cheap per-call containment layer INSIDE that already-confined process for the actual control-frequency invocation — never re-spawn or re-probe sandbox-exec per tick.
- Concretely for macOS process isolation options: sandbox-exec/Seatbelt is the ONLY macOS mechanism that gives a real kernel-enforced file-effect boundary (no bwrap/Landlock equivalent exists on Darwin, and App Sandbox needs code-signing/entitlements unsuited to a dev harness) — build the SBPL profile exactly like seatbeltProfileArgs (allow-default + deny file-write* + literal/subpath allow-list over CANONICALIZED/realpath-resolved roots, since Seatbelt matches resolved paths and /tmp IS /private/tmp on Darwin). subprocess+rlimit (resource.setrlimit) gives NO filesystem/network confinement at all — treat it purely as a resource-budget backstop (CPU time via RLIMIT_CPU/SIGXCPU, fd count, file size), analogous to computeMs/maxWallMs, layered ON TOP of Seatbelt rather than instead of it; note RLIMIT_AS/RLIMIT_DATA (memory) enforcement is unreliable on Darwin, unlike CPython having no in-process heap cap comparable to V8's resourceLimits.maxOldGenerationSizeMb — the honest fallback is a watchdog polling RSS and killing on overshoot, the same 'not proactively enforced, detected via exit' pattern the worker-thread backend uses for OOM (surfaced only as a post-hoc worker-exit). A Python-level restricted-exec 'namespace' (RestrictedPython, pruned globals/__builtins__) is NOT process isolation and must never be sold as the security boundary — it is at best a defense-in-depth layer INSIDE an already Seatbelt-confined process, since CPython has well-known sandbox-escape primitives (__subclasses__, ctypes, ctypes-via-object-graph, ...).
- Latency budget reality for 'control frequency': paying sandbox-exec profile install + fork/exec + fresh CPython interpreter cold start per call costs on the order of 20-60ms (SBPL parse+kernel policy install a few ms, fork/exec 1-5ms, CPython cold start 15-40ms+ depending on imports) — incompatible with anything faster than roughly 10-20Hz if paid per tick. To hit real control-loop frequencies (tens to thousands of Hz), amortize exactly like the harness does: probe/spawn the Seatbelt-confined worker ONCE per session/episode, then drive many calls through a persistent IPC channel (a local pipe/socket round-trip on macOS is sub-millisecond) into a LONG-LIVED interpreter that re-executes a PRE-COMPILED code object (compile() once, exec(code, fresh_locals) per tick) rather than re-parsing/re-importing per call — this is architecturally the 'persistent REPL-style kernel' the dsh-code-runtime README explicitly flags as unshipped future work ('the no-state-between-runs contract stands until a persistent-kernel backend brings its own logging story'), which a control-frequency critic runtime cannot avoid building.
- Budget enforcement inside that persistent worker cannot reuse Worker.terminate()'s clean semantics: CPython has no safe, forceful mid-execution interrupt of arbitrary hostile code from another thread (threads share the GIL, can't be force-killed; signal.alarm/SIGALRM only fires between bytecode ops on the MAIN thread and won't interrupt a tight native-extension loop). The two honest options, both weaker than the worker-thread's hard terminate(): (a) run each critic invocation in its own short-lived multiprocessing.Process so a hung/hostile call can be SIGKILL'd without taking down the persistent supervisor — but this reintroduces fork overhead per call unless the child is itself kept warm/pooled and only recycled on timeout; or (b) accept a soft, best-effort SIGALRM/watchdog-thread timeout that cannot guarantee termination of native code, and treat any budget overrun as cause to RECYCLE the whole worker process rather than trusting it stayed contained — mirroring the CodeRunFailure 'worker-exit' kind's honesty that the runtime cannot always distinguish 'the substrate died cleanly' from 'it's still running something you can no longer see.'
- Adopt the two-channel error taxonomy: report a per-call CodeRunFailure-style discriminated result (exception / timeout / abort / worker-exit / invalid-output / output-limit) as a RETURNED field from your critic-invocation function, never as a raised Python exception that the control loop must catch — this keeps the hot loop's error handling a plain branch on result.kind instead of exception-driven control flow, and keeps 'the critic program failed' cleanly separate from 'the harness itself misbehaved' (the latter should still raise, exactly as run() only rejects for Service Definition contract misuse).
- Report enforcement completeness truthfully rather than a boolean. If any layer of the Python isolation stack is partial (e.g., memory cap is watchdog-based/racy, or the confined worker inherits some ambient capability for process-init reasons), expose that as an explicit 'partial' status on every invocation result the way ConfinedArgv.enforcement does for windows-acl — never claim 'sandboxed: true' for a boundary you know has documented gaps.
- Separate the 'denial dialect' from the 'runner-failure dialect' if you build any string-matching classification of a failed confined call: a policy DENIAL (Seatbelt blocked a write — 'operation not permitted' in stderr) and a RUNNER FAILURE (sandbox-exec itself couldn't start, or crashed before running your code) mean opposite things for retry/escalation logic and must not be inferred from exit code alone.

**ANTIPATTERNS**
- A Python-level restricted-exec sandbox (RestrictedPython, exec() with a pruned __builtins__/globals dict, AST whitelisting) treated as sufficient isolation on its own. CPython exposes well-documented escape hatches (object.__subclasses__(), gc.get_objects(), frame/generator introspection, ctypes if importable) that make in-process restriction bypassable by a sufficiently adversarial program; even the harness's own worker-thread backend — a REAL separate V8 isolate, empty env, capped heap, hard terminate() — is explicit that it is 'containment, not a security boundary' (code-runtime-worker-thread/README.md). A pure language-level restriction is strictly weaker than that and must never be presented as the security boundary.
- Spawning a fresh sandbox-exec-wrapped Python interpreter per control-loop tick. Profile install + fork/exec + interpreter cold start runs tens of milliseconds — the whole reason dsh-sandbox-local's runner selection is probed and cached ONCE 'for the provider lifetime' (sandbox-local/README.md) rather than re-probed per confine() call; doing the equivalent per tick in Python destroys any real-time control budget.
- Treating resource.setrlimit as a security boundary rather than a resource-budget backstop. It bounds CPU time, fd count, and (unreliably on Darwin) address space, but grants zero filesystem or network confinement — it is the Python analogue of computeMs/maxWallMs (a containment budget), not of ctx.sandbox.confine() (a kernel-enforced effect boundary), and conflating the two is exactly the mistake the harness's own two-seam split (sandbox vs code-runtime) is designed to prevent.
- Assuming a passing probe or a successfully spawned wrapper proves confinement held for THIS run. dsh's RunnerFailureRule design exists specifically because 'exit status alone never proves runner failure' — a Python equivalent must not collapse 'the sandbox wrapper process started fine' and 'the policy actually applied to this exact invocation' into one boolean; a hostile or buggy critic program that crashes the wrapper before the profile takes effect must be distinguishable from one the profile legitimately denied.
- Letting a nested/programmatic invocation path (e.g., a critic-generated helper calling another tool/function) skip the policy pipeline that a top-level invocation goes through. dsh's code-mode.ts deliberately routes EVERY nested tool dispatch through the identical prepare/dispatch/finalize/finish scheduler stages as native top-level calls — a Python control-frequency design that gives 'fast path' calls from inside already-running critic code a shortcut around approval/denial policy reintroduces exactly the bypass this architecture was built to close.
- Silently degrading to no isolation when the sandbox backend is unavailable (missing sandbox-exec, e.g. a hypothetical future macOS without it). The entire seam's contract is fail-closed: 'refusing to run the command unconfined' — a Python control-frequency runtime must throw/refuse rather than fall back to an unconfined subprocess just because the fast path failed to establish.

- rate < 1.0 branch (the default, 0.5): required = ceil(N * rate); rescued = seeds where candidate succeeded and parent failed; passed = candidate_successes >= required AND candidate_successes > parent_successes AND rescued non-empty AND every rescued seed had both action divergence and a Role1 intervention AND candidate_safety <= parent_safety.
`p_value = None`, `alpha = None`, `conclusive = True` unconditionally. There is no significance test on this gate at all.

**Held-out gate — one-sided exact McNemar (conditional binomial sign test) on paired discordant seeds**

The test (gating.py:12-25):
```
discordant = candidate_wins + parent_wins   # b + c of the 2x2 paired table
if discordant == 0: return 1.0
p = sum_{i=candidate_wins}^{discordant} C(discordant, i) / 2**discordant
```
That is exactly P[X >= candidate_wins] for X ~ Binomial(discordant, 0.5): the one-sided EXACT McNemar test, conditioning on the number of discordant pairs. No continuity correction, no chi-square approximation, no ties handling beyond dropping concordant pairs.

Decision (gating.py:236-262):
```
p_value    = one_sided_exact_mcnemar(candidate_wins, parent_wins)
conclusive = (p_value < alpha) if heldout_require_significance else True
gain       = candidate_successes - parent_successes
success_rate = candidate_successes / len(expected_seeds)
passed = conclusive and gain >= heldout_min_gain
              and success_rate >= heldout_min_success_rate
              and candidate_safety_events <= parent_safety_events
```
Defaults: alpha=0.025 (one-sided, i.e. a one-tailed 0.05-equivalent), min_gain=1, min_success_rate=0.0, require_significance=True. `GateDecision.__post_init__` additionally forbids `passed and not conclusive`.

Consequence of the exact test with alpha=0.025 and strict `<`: the minimum evidence that can ever pass is a clean sweep of 6 discordant pairs (6-0 -> 1/64 = 0.015625 < 0.025). 5-0 gives 0.03125 and FAILS. 8-1 gives 9/256 = 0.0352 and fails; 9-1 gives 10/512 = 0.0195 and passes.

Two held-out shapes exist:
- `evaluate_fixed_heldout_20` (kind `heldout_20`, `statistical_contract='fixed_paired_mcnemar_20'`): requires exactly 20 preregistered seeds, evaluates all 20 in one look. This is the shipped default (`--heldout-count 20`, `--fixed-heldout-seeds 1-20`).
- `evaluate_two_stage_heldout` (kinds `heldout_10` / `heldout_50`): requires exactly 50 preregistered seeds; stage 1 = `preregistered_seeds[:10]`, stage 2 = all 50 (nested, includes the stage-1 ten). `_active_pairs` expands from 10 to 50 ONLY when the stage-1 decision was `not conclusive`; alpha is applied unchanged at both looks.

All seeds/policy_rng for held-out gates come from `manifest.heldout_seeds` (`_preregistered_seeds`), the plan binds `paired_seed_sha256 = canonical_sha256(list(seeds))`, and `_validate_plan` re-checks the seed binding, the statistical contract keys, and (schema_version>=3) the entire heldout policy dict on every re-read. Parent-evidence adoption is explicitly disallowed for held-out gates, so both arms are freshly executed.

*why:* McNemar is the right test for paired binary outcomes with the same physical reset; conditioning on discordant pairs removes the nuisance of the shared base rate. The exact form avoids the chi-square approximation breaking at the tiny discordant counts (often <10) this regime produces. min_gain/min_success_rate exist so statistical significance alone cannot promote a practically-null change.

**Failure segmentation and the 'earliest divergence step' localization**

The literal phrase 'Earliest Observable Divergence' does not appear in the code; the operational field is `FailureSegment.earliest_divergence_step: int | None` (models.py:245).

`trajectory.py::_segments` runs, only on episodes with `success is False`, six ordered detectors over a merged event stream built from four strict JSONL artifacts (chunks, actions, states, tools). Each detector returns a `_Signal(priority, failure_class, stage, tool, step, summary, severity)`:
- priority 0 `_safety_event` (`out_of_bounds` / `safety_violation` true, or those tokens in the event type), severity 1.0
- priority 1 `_critic_reject`, `_role1_contract_failure` ('role1_contract_failure' in event type), `_tool_error` (payload has `error`, or `ok is False` / `success is False` / `failed is True`, or event type contains tool_error/failure/failed/exception), severity 0.95-1.0
- priority 2 `_explicit_no_progress` (`no_progress`/`stagnant` true or in event type), severity 0.85
- priority 3 `_early_termination` (`early_termination`/`role1_terminated`/`terminate` true AND `authoritative_success is not True`), severity 0.9
- priority 2 fallback `_window_no_progress`: only added if no structured no_progress signal exists. It scans state rows for a monotone progress scalar (`task_progress|progress|completion`, or any key ending in `residual_to_success|distance_to_goal|goal_distance`, sign-inverted so bigger = better) and flags the FIRST window of `no_progress_window=8` consecutive observations whose range <= max(1e-4, |v0|*1e-3) — but only if there was prior measurable progress or a `*target_contact is True` in the window. severity 0.8
- priority 4 `_fallback_incomplete`: emitted ONLY when nothing else fired; failure_class `horizon_incomplete`, step=None, severity 0.6. The comment states the reason: attaching it to every failed trajectory would manufacture an artificial 100%-prevalence cluster.

Dedup: one segment per (failure_class, stage, tool) key, keeping the one with the smallest (step, priority). Each segment's window is `[max(0, step - context_before=8), min(observed_end, step + context_after=8)]`. `segment_id = 'segment-' + sha256(episode_id, failure_class, stage, tool, earliest_divergence_step, start_step, end_step, artifact_sha256 map)[:24]` — i.e. segment identity is content-addressed over the immutable artifact digests.

Critical `None` semantics: `earliest_divergence_step=None` means 'known failure, but the evidence does not localize the first divergence'. The dataclass comment is explicit that encoding it as step 0 'poisons shadow-replay lead-time/recall statistics', and `__post_init__` branches its interval invariant on it.

*why:* Gives every failed episode a small, deterministic, content-hashed causal window instead of a whole trajectory — this is what clustering, Stage-1 evidence budgeting, and shadow-replay lead-time all key off. The priority ordering encodes 'a structured safety/tool error is a better divergence witness than a statistical stagnation guess'.

**Deterministic failure clustering: hard partition + complete-link agglomeration + medoid**

`clustering.py::cluster_failure_segments(segments, similarity_threshold=0.72, representatives=3)`.

Step 1 — HARD partition: segments are bucketed by the exact triple `(failure_class, stage, tool or '')`. Segments in different buckets can NEVER merge, regardless of text similarity.

Step 2 — similarity within a bucket (`segment_similarity`): weighted mean of up to three cosines, weights normalized by the weights actually present —
  * token-count cosine over `[a-z0-9_-]+` tokens of `summary`, weight 0.6 (always present)
  * cosine of `segment.embedding`, weight 0.3, only if the vectors are non-empty and same-length; negatives clamped to 0
  * cosine of `segment.state_signature`, weight 0.1, same conditions
The `embedding` is NOT a learned model: `trajectory.py::_text_embedding` is a deterministic 32-dim signed hashing trick (sha256 per token -> bucket = first 2 bytes mod 32, sign = bit 0 of byte 2), L2-normalized, rounded to 8 decimals. `state_signature` is the first 16 finite numeric scalars from state rows inside the segment window, rounded to 6 dp, with agent-forbidden keys filtered.

Step 3 — `_complete_link_clusters`: greedy agglomerative with COMPLETE linkage (`similarity = min` over all cross pairs), repeatedly merging the highest-similarity pair >= threshold. Ties broken deterministically by the sorted tuple of member segment_ids. The docstring gives the reason: complete link stops an A~B~C chain from merging A and C whose mechanisms are dissimilar.

Step 4 — ranking and representatives: clusters sorted by `(-size, -sum(severity), hard_key, first segment_id)`, then assigned `cluster-001`, `cluster-002`, .... For each cluster `pair_scores[m] = sum of similarity(m, other) for all members`; `medoid = argmax(pair_scores)` (tie -> lowest segment_id); `representative_segment_ids` = top-3 by `(-severity, -pair_score, segment_id)`. `prevalence = len(members) / total_segments`; `mean_severity = mean(member severities)`. Cluster `summary` is the medoid's summary.

Step 5 — TARGET selection is a separate, harness-owned re-ranking (`lifecycle.py::materialize_cluster_targets`): clusters are re-sorted by `(-unique_episode_count, -prevalence, -mean_severity, cluster_id)` and only the top 2 become ranked targets. Each target is frozen as `target_sha256 = canonical_sha256({manifest_sha256, cluster_report_sha256, cluster_id, rank, episode_ids, member_segment_ids})` and written once to `analysis/cluster_targets.json` (re-running must reproduce the identical hash or it raises). `ranking_authority` is recorded as `harness_unique_failure_episode_count` — deliberately overriding the agent's own `dominant_cluster_id`.

Optionally an LLM Cluster Agent re-partitions on synchronized video (`_materialize_multimodal_cluster_review`): it may regroup segments into `visual-cluster-<sha[:16]>` groups with `hard_key=('multimodal_review','generation_batch','group_NNN')`, but the output must carry `deterministic_source_sha256` equal to the hash of the deterministic report, and segment ids are round-tripped through blinding aliases so the agent never sees raw ids or seeds.

*why:* Failure clusters are the unit of learning, so they must be reproducible from immutable evidence and not manufactured by a model. Hard partitioning + complete link + medoid gives a stable, defensible 'these failures are the same mechanism' claim; harness-owned target ranking by unique-episode support prevents an agent from steering the campaign at a rare-but-vivid cluster.

**Shadow replay — offline detector validation on immutable parent trajectories**

`shadow_replay.py::evaluate_shadow_replay` is READ-ONLY: it replays only the candidate's DELTA critic rule(s) (`candidate.critic_rules` minus rules whose `rule_id` is in the parent bundle) against stored `states.jsonl` rows. It hard-requires `len(delta_rules) == 1`.

Inputs: `target_records` = the (record, states_path) pairs for the target cluster's episodes (falls back to 'all valid failures' only for a legacy diagnosis row); `success_controls` = every valid SUCCESSFUL episode with a states artifact. Every input must have `status=='valid'` and `bundle_sha256 == candidate.parent_sha256`, else it raises.

Per trajectory it constructs a fresh `TemporalCritic(delta_rules)` and steps every row in order:
- `first_trigger_step` = first `step_index` where the rule emits a proposal
- `divergence` = `min(seg.earliest_divergence_step for seg in record.all_failure_segments if not None)`, else None
- `triggered_before_or_at_divergence = first_trigger is not None and divergence is not None and first_trigger <= divergence`
- `lead_time_steps = divergence - first_trigger`
- KeyError handling is asymmetric and deliberate: a missing feature BEFORE any successful evaluation is treated as an un-instrumented reset prefix (step recorded in `unavailable_feature_prefix_steps`, continue); a missing feature AFTER at least one successful evaluation sets `replay_evaluable=False` with reason `required_critic_features_changed_during_replay` and breaks. Never evaluating at all -> `required_critic_features_never_logged`. It fails CLOSED to 'inconclusive, require online evidence' rather than crashing or inferring a detector failure.

Metrics: `target_detected` = count of KNOWN-divergence targets triggered at-or-before divergence; `target_recall = detected / len(known_target)` (None if no known-divergence targets); `success_control_false_positives` = count of controls where the delta rule triggered ANYWHERE in the trajectory; `success_control_false_positive_rate = fp / len(controls)` (None if no controls). `feature_schema_sha256 = canonical_sha256(sorted(all scalar feature names seen))`. `report_sha256 = canonical_sha256(report)`.

Gating flags: `preflight_conclusive = bool(controls) and every target has a known divergence and every outcome is replay_evaluable`. `passed_detection_preflight` additionally needs `detected == len(target)` and `false_positives == 0`.

Enforcement in `run_proposal_stage` (lifecycle.py:4529-4586): a PRE-check `_candidate_feature_contract` first requires that, for EVERY replay trajectory, the delta rule's feature and all its activation-condition features co-occur in at least one state row AND in every row from that point onward (a sparse feature that disappears mid-trajectory is rejected up front). Then `detection_rejected = preflight_conclusive and target_detected != target_count` -> raises. `_shadow_live_gate_admission` separately computes the false-positive verdict: `exceeded = observed_rate > shadow_success_control_max_false_positive_rate` (default 0.0, i.e. strict zero FP), and `eligible_for_live_gate = not exceeded`. Both the report and a `precommit.json` (candidate_sha256, parent_bundle_sha256, shadow_report_sha256, sorted target trajectory sha256s) are written with `overwrite=False` before the candidate is registered.

The report itself carries the honest limitation string: read-only replay validates DETECTION only; it cannot establish recovery causality because new actions produce a different future. That is precisely why the same-seed gate exists downstream.

*why:* Cheap falsification before spending simulator time: a critic that never fires on the failures it was written for, or that fires on trajectories that succeeded, is rejected offline. It is a detector precision/recall preflight, explicitly not a proof that the recovery works.

Publish the induced minimum-evidence table alongside it (with alpha=0.025 the floor is a 6-0 sweep) so nobody designs an underpowered block by accident.
- Separate the gates by what they can establish, and say so in the artifact. Shadow replay = detection only (its own report carries the limitation string 'cannot establish recovery causality because new actions produce a different future'); same-seed = causal intervention on the exact observed failures; held-out = generalization. Never let one substitute for another.
- Enforce the atomic-delta rule in code, not in the prompt. `_require_atomic_parent_inheritance` (parent rules byte-identical + exactly one new critic + exactly one new recovery + the new recovery may only be triggered by the new critic) is ~40 lines and is what makes the paired gate a causal claim about one change. Pair it with a semantics-only hash (`_mechanism_semantics_sha256`, excluding ids/titles/evidence) so a refinement cannot resubmit the same behavior under new names.
- Make `earliest_divergence_step` genuinely nullable and propagate the nullability into the statistics. Coding 'unlocalized' as step 0 silently inflates recall and lead-time; here `target_recall` uses a known-divergence denominator and the whole preflight is marked inconclusive when any target is unlocalized.
- Hard-partition failure segments by (failure_class, stage, tool) BEFORE any similarity clustering, and use complete linkage inside a bucket. This kills the two classic failure modes: cross-mechanism chaining, and a catch-all bucket. Also keep the 'never emit the generic horizon-incomplete signal unless nothing else fired' rule — otherwise you manufacture a 100%-prevalence cluster that hides everything actionable.
- Let the harness, not the agent, rank which cluster to attack (`ranking_authority: harness_unique_failure_episode_count`) and freeze the choice as a `target_sha256` over {manifest, cluster report hash, cluster_id, rank, episode_ids, segment_ids}. The agent's own `dominant_cluster_id` is recorded but not obeyed.
- Run a feature-availability precheck before the expensive replay: require every critic feature and activation-condition feature to co-occur in at least one state row and in every row thereafter, per trajectory. This catches the 'privileged value only present at reset' and 'sparse feature disappears mid-episode' bugs at proposal time instead of mid-gate.
- Reuse frozen parent evidence for in-distribution gates (adopt the Loop-1 rollout record as the parent arm, with an immutable adoption row, refused once any parent dispatch exists) but FORBID adoption for held-out gates so both arms run live. This halves simulator cost exactly where the parent arm is provably identical and nowhere else.
- Classify infrastructure failures as a third outcome that never enters a denominator, retry them under a bounded budget, and require an explicit, evidence-checked `authorize_infrastructure_recovery` artifact to extend that budget — with the code verifying every exhausted attempt really was infra-invalid.
- Commit an early mathematically-impossible rejection (`_early_impossible_same_seed_decision`) once the remaining arms cannot reach the threshold. On a physical harness this is a large wall-clock saving and it is provably not a bias, since it can only reject.
- Blind agent-facing evidence structurally: strip any key containing seed/rng/path, strip a private-key set, regex-redact locators from free text, and address artifacts only through keyed content-ids. Do this at the serialization boundary, not by asking the model to ignore things.

**ANTIPATTERNS**
- `heldout_mode='test'` promotes on FAILURE. In `record_gate_and_advance` (lifecycle.py:4694-4700) a held-out decision in test mode routes to PROMOTE regardless of `decision.passed`, and `store.promote` only checks that a held-out decision EXISTS ('may be false' per its own comment). With test mode, the actual promotion criterion is: the same-seed gate passed. Do not copy the shape without deciding, per campaign, whether held-out is advisory or blocking — and never describe a test-mode run as 'gated on held-out seeds'.
- The same-seed gate has NO statistical test. `evaluate_paired_gate` is called for kind='same_seed' with `alpha=None`; the branch returns `p_value=None, conclusive=True` and decides by `candidate_successes >= ceil(N * 0.5)`. Worse, N is the number of distinct failing dev seeds in the target cluster and can be 2-3, so the default rule degenerates to '1 of 2 rescued'. And these are the very seeds the diagnosis was written from — it is an in-sample threshold, not a test. If this is the de facto promotion gate (as it is in test mode), it needs either a real test or a much larger N.
- The regression gate is skipped by default. `prepare_libero_campaign.py:557` computes `regression_required = not bool(getattr(args, 'skip_regression_gate', True))` and the CLI flag itself defaults to `True` (line 744-748). So out of the box nothing checks that the candidate did not break the other ~47 development seeds. The README's flow diagram omits regression entirely, which reads as intentional but should be stated, not inferred.
- Default drift between the three places the policy is defined. `EvolutionProtocol.heldout_mode` defaults to `'test'`; `lifecycle._evolution_policy` and `gate_runner._heldout_policy` default the SAME key to `'validation'` when absent from a manifest; the prepare CLI defaults to `'validation'` while the README example passes `test`. Same divergence on `maximum_total_candidate_rounds` (protocol 25 vs prepare CLI 15 vs lifecycle fallback `per_cluster * clusters`) and `max_candidate_rounds_per_cluster` (protocol/CLI 8 vs lifecycle fallback 5). Reimplement with ONE default source; a policy default that differs by reader is a silent-protocol-change bug.
- The legacy 10->50 held-out path is an unadjusted two-look sequential test. `_active_pairs` expands from `pairs[:10]` to all 50 only when the stage-1 decision was inconclusive, and `evaluate_two_stage_heldout` applies the SAME alpha=0.025 at both looks with no alpha spending (no Pocock/O'Brien-Fleming). The stage-2 block also NESTS the stage-1 ten seeds, so the two tests are strongly dependent. Actual family-wise type-I error exceeds the nominal 0.025. The shipped default (`heldout_20`, single look on 20 seeds) does not have this problem — prefer it, or implement real alpha spending.
- No multiplicity correction across candidate rounds. Up to `max_candidate_rounds_per_cluster` (8) candidates per cluster and `maximum_total_candidate_rounds` (15-25) per campaign are proposed and screened against the same same-seed evidence, and in validation mode the survivor gets one alpha=0.025 held-out look. `heldout_max_rounds=1` bounds the held-out looks, which is the saving grace — but the selection pressure upstream is uncorrected and the reported p-value is a post-selection p-value. Report it as such.
- Shadow replay's false-positive measurement is vacuous when the parent has no successes. `_shadow_live_gate_admission` computes `observed = fp/control_count if control_count else None`, and `exceeded = observed is not None and observed > limit` -> a candidate with ZERO success controls is `eligible_for_live_gate=True` with disposition `not_evaluated_no_success_controls`. On a hard task where the parent policy never succeeds, the false-positive gate silently does nothing. Require a minimum control count or fail closed.
- Shadow replay only BLOCKS when `preflight_conclusive` is true. `detection_rejected = preflight_conclusive and target_detected != target_count`; `preflight_conclusive` requires success controls to exist AND every target to have a known divergence step AND every outcome to be replay-evaluable. Any one unlocalized target makes the whole recall check advisory. Honest, but it means 'passed shadow replay' frequently means 'shadow replay had no opinion'.
- `_candidate_intervened` falls back to a string prefix scan. When `artifact_index['candidate_intervention']` is absent it returns `any(str(key).startswith('role1:') for key in record.artifact_index)`. The `mechanism_diverged` requirement — the thing that stops a no-op bundle passing on simulator noise — therefore rests on an artifact-key naming convention for legacy records. Make the attestation mandatory and typed in a new implementation.
- `_same_physical_reset` weakens the reset binding to a single `state_sha256`, explicitly allowing camera-digest mismatches (counted into the rationale text only). The comment justifies it — exact camera bytes are not stable across EGL contexts — but the consequence is that 'bit-identical reset' is really 'identical recorded physical state digest'. If your harness can make renders deterministic, keep the stronger binding.
- Same-seed gate plans at the current `schema_version = 3` skip cluster-lineage revalidation. `_validate_plan` guards the cluster_report_sha256 / cluster_target_sha256 / pass-rate checks behind `if self.gate_kind == 'same_seed' and version == 2:` — so freshly written v3 plans never re-verify their cluster lineage on re-read. The pass rate is still validated at use time by `effective_same_seed_gate_pass_rate`, but the lineage check is simply dead for new campaigns. Looks like an unmigrated version guard.
- Multiple operator override paths can lower the bar mid-campaign: `authorize_same_seed_threshold_override` (reduce the required same-seed successes and optionally skip regression), `authorize_provisional_hypothesis` (gate on an INCONCLUSIVE diagnosis), `authorize_shadow_falsification` (relax the zero-false-positive shadow limit), `transition_timeboxed_same_seed_to_heldout`, and `store.reopen_completed_provisional_hypothesis` (reopen a COMPLETE campaign). Each is well-built — candidate-bound, hash-identified, ledgered, refused once a decision or the held-out gate exists — but collectively they mean a promoted result is only as strong as its authorization ledger. Any reimplementation must surface these in the headline result, not just in the audit trail.
- `decision_id` does not bind the held-out policy when the policy equals the defaults: `evaluate_paired_gate` only adds `heldout_policy` to the hashed `decision_payload` when alpha/min_gain/min_success_rate/require_significance differ from (0.025, 1, 0.0, True). Minor, but it means two decisions under different-but-default-looking contracts could collide. Always hash the full effective policy.
- Manifest `expected_heldout` defaults to 50 in the dataclass while the prepare CLI defaults `--heldout-count` to 20; `_preregistered_seeds` then hard-requires len==50 for kind 'heldout' and len==20 for 'heldout_20'. It works because `heldout_gate_kind` is derived from the count, but the two-source default is fragile. Derive the gate kind from one place.

### Action-frequency temporal critic + frozen recovery: schemas, evaluation semantics, observation feature contract, role bo


**CriticRule / CriticPredicate schema and (weak) validation**

CriticRule is a frozen slotted dataclass: rule_id, title, feature (dotted string), operator (Literal lt|le|gt|ge|eq|ne|stagnant), threshold (float|int|str|bool), dwell_steps:int, cooldown_steps:int, proposal:str, evidence_ids:tuple, safety_only:bool=False, activation_conditions:tuple[CriticPredicate,...]=(). __post_init__ enforces ONLY three things: feature.strip() non-empty, dwell_steps>=1 and cooldown_steps>=0, and evidence_ids non-empty. CriticPredicate is feature/operator/threshold with only a non-empty-feature check. Crucially the operator Literal is NOT enforced at runtime: an unknown operator survives construction and blows up as a KeyError inside the dict dispatch in TemporalCritic._condition/_predicate at the first evaluated step. threshold types are never checked against the operator, so a numeric operator on a bool/str feature raises TypeError mid-episode rather than at candidate-admission time. Real admission checks live one layer up in zetta/evolution/stages.py: _reject_collision_control (no 'collision' substring in any rule/predicate feature name and no /\bcollisions?\b/i in any proposal/precondition/stop_condition/fallback/stop_when text), the observed-feature-catalog check, _validate_recovery_tool_parameters, _validate_recovery_chunk_policy, and _require_atomic_parent_inheritance.

*why:* The rule is a machine-executable, content-addressed artifact written by an LLM (Stage2) and then frozen for a whole campaign generation. Keeping the dataclass permissive but the stage validator strict lets historical bundles rehydrate byte-for-byte (digest stability) while new proposals get the tighter gate. The collision ban is explicit policy: MuJoCo contact telemetry is treated as diagnostic-only and may never gate online control.

**TemporalCritic.evaluate: per-rule state machine (dwell, cooldown, activation epochs)**

State is one _RuleState per rule_id {consecutive:int, cooldown_remaining:int, history:list}, constructed once and persisted across every evaluate() call for the whole episode; reset() re-creates it per episode. Per step, per rule, in rule declaration order:\n1. value = resolve_feature(observation, rule.feature) — evaluated BEFORE the activation guard, so a missing primary feature raises KeyError even when the guard would have been false.\n2. If any activation_condition is false: consecutive=0, cooldown_remaining=0, history.clear(), continue. A false guard therefore starts a fresh temporal epoch AND cancels any pending cooldown.\n3. Else append value to history and truncate to the last dwell_steps entries.\n4. If cooldown_remaining>0: decrement, consecutive=0, continue. Cooldown only ticks on steps where the guard holds.\n5. condition = _condition(rule, value, history). For 'stagnant': require len(history)>=dwell_steps then max(history)-min(history) <= threshold. For everything else: plain scalar comparison of the current value only.\n6. consecutive = consecutive+1 if condition else 0.\n7. required_consecutive = 1 for 'stagnant' (the window already encodes the dwell) else dwell_steps.\n8. On consecutive>=required: emit a proposal dict {rule_id, step_index, feature, observed_value, activation_conditions (each echoed with its observed_value), proposal, safety_only, environment_write: False}, then consecutive=0 and cooldown_remaining=rule.cooldown_steps.\nAll firing rules emit in one list; there is no priority, no dedup, no cross-rule state.\n_numeric() rejects bool explicitly and requires finite floats, so bool features are only comparable with eq/ne (which use raw Python ==/!=).

*why:* It is deliberately the smallest expressible online monitor: a per-feature threshold with hysteresis (dwell) and rate limiting (cooldown), plus a variance-window 'stagnant' operator for the dominant failure mode (a VLA that keeps emitting commands while nothing physically moves). Activation conditions exist so a post-contact rule cannot be satisfied by pre-contact history — the epoch reset is the mechanism that enforces that.\nWhat it CANNOT express: any relation between two features (no a-b, no ratios), any boolean OR (activation_conditions are pure AND), any temporal operator other than 'N consecutive' and 'window variance' (no EWMA, no derivative, no 'was true within the last K steps'), any cross-rule or stateful counting beyond consecutive/cooldown, and any per-rule severity or priority. Every derived quantity (velocity, progress delta, direction cosine, stagnation of a command vs. realized motion) must be precomputed into the feature dict by the extractor.

**resolve_feature: flat-key-first dotted path resolution**

resolve_feature(observation, dotted_path) first tries the whole dotted string as a single flat dict key (which is exactly what the LIBERO extractor emits: keys literally named 'privileged.task.manipulated_object.grasped'), and only on a miss splits on '.' and walks nested dicts. *why:* The runtime plane is flat for cheap JSONL logging and hashing (canonical_sha256 over the flat dict is the per-step observation digest); test/diagnostic fixtures are nested. **stop_when / stop_condition / fallback are NL prose, not executable predicates**

**VLA re-entry contract: chunk interruption, proposal acknowledgement, rule suppression**

The VLA runs as bounded chunks. When a bundle is active, _vlm_chunk sends the whole chunk through env.critic_chunk_step(actions, critic_rules=..., interrupt_on_proposal=True); the server steps actions one at a time, recomputes features + privileged state per step, evaluates the frozen critic, and BREAKS the loop at the first step that produces any proposal — the remaining planned actions are discarded, so the VLA is always re-queried from a fresh post-interruption observation. Proposals are then filtered client-side by _filter_suppressed_proposals and handed to handle_recovery, which activates a recovery and loops Role1 decisions until the frozen steps complete. Three subtleties: (a) primitives.suppress_recovery_rules(trigger_rule_ids) is a CLIENT-side filter only — the server keeps evaluating the full frozen rule set, so the audit trace is unaffected; it exists so the very rule that authorized the recovery cannot recursively interrupt it. **REUSABLE**
- Adopt TemporalCritic verbatim as the online monitor core. It is ~100 lines, has zero dependencies beyond math, and its per-rule state machine (dwell → consecutive count, cooldown → rate limit, activation_conditions → temporal epoch reset) is exactly the right minimum for a physical harness. Keep the two non-obvious details: (a) a false activation guard clears history AND cooldown, and (b) 'stagnant' needs required_consecutive=1 because the window itself supplies the dwell.
- Adopt the flat-dotted-key feature plane with a single extractor function as the ONLY producer. One function, called on every physical step, that raises on malformed input and enforces a namespace prefix for anything privileged. Hash the flat dict per step (canonical_sha256) and log it as JSONL — that artifact is simultaneously the audit trail, the shadow-replay input, and the source of the feature catalog.
- Adopt the empirically-derived feature catalog (_observed_critic_features) instead of a hand-maintained constant list. A rule author may only bind names that were actually logged, and for fresh proposals only names present on ACTION rows (command.available==True), not reset-only rows. This kills hallucinated features and reset-only predicates at admission rather than at runtime. Pair it with the co-occurrence check (_candidate_feature_contract) so a rule and all its activation predicates provably appear together in at least one row.
- Adopt the coverage invariant: every critic rule must be covered by at least one recovery rule, enforced in the bundle's __post_init__. A monitor that can reject an action without a frozen executable alternative is a deadlock generator. Also adopt the append-only atomic delta (parent rules byte-for-byte + exactly one new critic and one linked recovery per generation) — it is what makes a paired gate a causal experiment.
- Adopt the three-layer role boundary. Layer 1: proposals carry environment_write:False as DATA and payloads are recursively scanned for forbidden control claims. Layer 2: a single validate_* function with an exact allowed-field set and per-action-kind structural rules, refusing to coerce or default anything. Layer 3: one Actor object that owns the only handle to mutating primitives, that cannot invent a tool (it must equal the frozen step's tool), and that hard-checks the environment actually advanced. Persist decisions content-addressed with overwrite=False and require re-load-and-revalidate before activation.
- Adopt interrupt-on-proposal chunk execution: send the whole chunk to the env, let the env step it one action at a time and evaluate the critic per step, and BREAK at the first proposal, discarding the chunk tail. This is what makes control authority per-physical-step while keeping one RPC per chunk. Pair it with the acknowledgement primitive (begin_recovery_step clears the pending proposal so the recovery's first action may execute) and client-side rule suppression (the authorizing rule cannot recursively interrupt its own recovery, while the server still evaluates and logs the full frozen rule set).
- Adopt the RecoveryController as a separate episode-local, append-only, fsync'd step machine: single activation (never preempt an active recovery), deterministic selection (sort matches by id), tool-name equality required to advance, and executed_horizon>=1 required unless the tool self-reports no_op_verified. Its refusal to restore simulator state is the right scope — it is bookkeeping, not a transaction manager.
- Adopt the tool contract split between tools that can advance the environment and proposal-only tools that return no_op_verified=true / environment_advanced=false. It lets the 'did the world actually move' check stay a hard invariant for mutating tools while perception/planning tools legitimately return zero horizon. Adopt the parameter-schema closure too: the frozen catalog's input_schema.properties is the closed set a rule author may use, and extra kwargs are rejected at admission.
- Adopt the namespaced tool naming (short names in persisted bundles, '<robot>.<tool>' for the decision layer) with explicit translate functions that raise on unknown names, so a persisted decision from one embodiment cannot validate against another's catalog.
- Adopt the class-level extension injection trick if the harness wraps a vendored vectorized env worker: install on type(env) from inside the env factory, never on the instance, because 'reconfigure' replaces the instance wholesale. Return {'available': False} for unknown methods rather than raising, so a bad call cannot poison the worker pipe.
- For a REAL physical harness, build the critic feature plane out of Group A first and make it the default vocabulary: EEF pose from FK, gripper opening from finger encoders, commanded vs. realized motion, and the derived 'command.realization.stalled' predicate. **ANTIPATTERNS**
- Do NOT copy the assumption that the 'privileged.' prefix marks the sim-to-real boundary. It does not. episode.reward and episode.terminated are the LIBERO success oracle and live OUTSIDE the guarded prefix — a critic rule can bind them freely, and episode.terminated is even on the Role1 forwarding whitelist. Any harness that reuses this design must classify by sensor-derivability, not by name prefix.
- Do NOT copy privileged.task.target_identity_confidence = 1.0. A hardcoded perfect perception confidence teaches the rule writer that identity is free. On real hardware this is the quantity you most need to reason about, and a rule tuned against a constant 1.0 has no real counterpart. Same for privileged.task.{manipulated_object,target}.name being exact BDDL identity strings — that is perfect open-vocabulary grounding with zero ambiguity.
- Do NOT copy shaped distance-to-goal features (privileged.dishwasher.rack.residual_to_success / remaining_to_success_m, privileged.task.goal.progress, privileged.task.manipulated_object.distance_to_target_m used as a progress oracle). These are reward shaping smuggled into the observation plane; a critic keyed on them is measuring the evaluator, not the robot.
- Do NOT copy privileged.dishwasher.rack.success_direction_base at all. A unit vector pointing toward task success, already expressed in the ROBOT BASE FRAME, is an action label, not an observation. A recovery that projects a pending action onto it is being told the answer. This is the single worst privilege leak in the repo.
- Do NOT copy privileged contact CARDINALITY (privileged.contact.robot.count, .gripper.count) or named geom-pair contacts as control signals. No real sensor produces a count of simultaneous contact manifolds or the names of the two geometries involved. The repo already bans collision telemetry from online control (_reject_collision_control) — extend that ban to contact counts and per-pair evidence, keeping only aggregate wrench magnitude and per-fingertip contact booleans.
- Do NOT treat stop_when / stop_condition / fallback as if they do anything. They are natural-language prose that is never parsed, and 'fallback' has literally no runtime path — if the frozen steps exhaust, the recovery just completes. If your harness needs a fallback, make it an executable field (an extra RecoveryStep, or a typed predicate), not a string an LLM writes.
- Do NOT rely on the dataclass __post_init__ for rule validation. CriticRule accepts an arbitrary operator string and an arbitrary threshold type; the failure surfaces as a KeyError or TypeError mid-episode, inside the env worker, on some later seed. Validate the operator against the enum and type-check threshold against the feature's declared dtype at admission time.
- Do NOT reproduce the geometry-feature trap. Position/orientation features are logged, therefore in the observed catalog, therefore admissible as critic rule features — but the moment such a rule FIRES, LiberoRole1RecoveryActor raises 'Critic attempted to expose private geometry to Role1', retries 3×, and the episode is silently marked method-invalid. If a class of feature is forbidden downstream, exclude it from the catalog upstream.
- Do NOT duplicate the critic and the privileged sensors into two hand-maintained byte-aligned copies (zetta/robots vs rollout_runtime) to satisfy a layering test. The docstrings themselves admit the two implementations must never diverge or they will compute different trigger timings on the same trajectory. Extract a genuinely dependency-free shared package instead of enforcing alignment by comment.
- Do NOT let 'no_op_verified' be self-reported by the tool without an independent check. The Actor's environment-advanced invariant is currently escapable by any tool that returns no_op_verified=true and environment_advanced=false; the controller then advances the frozen step anyway. Verify against the env's own step counter rather than the tool's claim.
- Do NOT assume the cooldown is a real rate limit. cooldown_remaining is zeroed whenever the activation guard goes false, so a rule whose guard flickers can re-fire on consecutive steps regardless of cooldown_steps. If you need a genuine minimum inter-fire interval, track it on absolute step_index, not on a counter that the epoch reset clears.
- Do NOT publish absolute world coordinates into a recovery-tool contract and then rely on 'the geometry stays local to the audited tool' as the safety story (privileged_pick_place reading manipulated-object and target world XYZ; semantic_joint_interact consuming approach/press/tangent world points). Locality bounds the blast radius but not the capability: the tool is still executing a simulator-solved plan, so any success it produces does not transfer.
